# Mandalore 2.0 design

Mandalore 2.0 turns memory into a service. One server owns each signet. Every
agent reaches it over MCP, whether the server runs on the same machine or across
the internet. Plugins become thin: a URL, a hook and two skills.

File and type names refer to the repo at commit `4594487` (release 1.6.1).

## Why

In 1.x every device has its own Git clone of the signet. That causes three
problems:

- **Stale reads.** A device only sees another device's memory after both have
  synced. Sync depends on hooks and on the model, and the model sometimes skips
  it. This is why 1.3 had a hold.
- **Clunky install.** Each device needs a binding file, a hash-pinned runtime,
  a session policy and a generated `connection.sh`
  (`internal/install`, `internal/distribution`, `internal/sessionsync`).
- **Heavy context.** The hooks inject about 2.5 KB of policy text on every
  prompt (`memorycontext.SessionOrientation` plus `CrossAgentEvidence`), plus
  up to 4 KB of recall and the scope list (`internal/memorycontext/context.go`).

With one writer, reads are always current. Nothing has to sync before a read.

## 1. Server

### Shape

- A new command, `mandalore serve --config FILE`, runs one long-lived process.
- The process serves one or more signets. Each signet is isolated: its own Git
  checkout, its own writer lock, its own approved clients, its own MCP URL and
  its own token audience.
- The server is the only writer to each signet's Git repo. No agent writes to
  the repo directly. The `mandalore` CLI stays, as the admin tool on the server.
- MCP runs over Streamable HTTP. One signet uses `/mcp`. Several signets use
  `/s/<slug>/mcp`. The URL is the signet's identity for OAuth (`resource`).
- Local use is the same server on `127.0.0.1`. There's no separate stdio mode
  for agents.

### Storage and Git

- Git stays the store and the history. The on-disk format is unchanged
  (formats 1 and 2 in `docs/signet-format.md`). No format bump is needed.
- Writes go through the existing engine (`memory.Service.RememberIdempotent`,
  `AppendJournalIdempotent`, the visibility writes). It already validates the
  graph and writes a durable intent before publishing.
- After each write, the server commits and pushes to the remote as a backup.
  It reuses `internal/sync` (`Checkpoint`, then `Sync`). The push is debounced
  (a few seconds) and runs in the background, so a save doesn't wait on the
  network. A failed push is retried on a timer. The save receipt says
  `durable` and `backup: pending|pushed|failed`.
- Reads never fetch. The server is the writer, so its checkout is current.
  This removes the read-path `delivery()` call that `razor-crest` makes today.
- The server refuses to start if the remote has commits it doesn't have, unless
  an admin runs an explicit reconcile. After cutover nothing else should push.
  A surprise remote commit means a 1.x writer is still alive.

### Who wrote it

Today razor-crest writes every revision with the service's single binding
identity (`binding.OpenGuarded(..., "razor-crest", ...)`). Clients aren't
recorded, except inside the hashed idempotency key.

2.0 records the client on every write without changing the format:

- When the owner approves a client, the server enrolls a **device record** for
  it in `provenance/devices/` (for example label `Claude (claude.ai), approved
  2026-10-25`). Devices are already the format's "where did this come from".
- Each write uses `Authorship{DeviceID: <client device>, Actor: <owner name>,
  Harness: <client kind, e.g. "claude.ai" or "claude-code">}`.
  `memory.Service` needs a per-call author instead of a fixed one
  (`OpenService(root, author)` today). That's a small engine change.
- Recall hits already include `device_id`, so the model can see which client
  wrote a memory.

### Tools

Tools come from the existing catalog (`api.Catalog()`), filtered by scope:

- Read scope: `memory_scopes`, `memory_recall`, `memory_history`,
  `memory_journal`, `memory_visibility_history`, `memory_context` (new, see
  section 4), and the canon read tools.
- Write scope adds: `memory_remember`, `memory_journal_append`,
  `memory_withdraw`, `memory_restore`, `foundling_promote`,
  `foundling_canon_promote`.
- Gone from the agent surface: every `*_and_sync` tool, `memory_sync`,
  `memory_sync_status`, install, connection, release, migration and readiness
  operations. Those are admin work on the server, through the CLI.
- Writes keep the required `request_id` from razor-crest. The idempotency key
  stays namespaced by client.

Server instructions and tool descriptions get short. The server knows its own
state, so the long transport caveats in `memorycontext` go away. Target: server
instructions under 600 bytes.

### What razor-crest gives us

`internal/razorcrest` is about 670 lines. Roughly 60% carries over:

| Part | Reuse |
| --- | --- |
| Streamable HTTP handler (`sdk.NewStreamableHTTPHandler`, stateless, JSON responses, 64 KiB body cap, cancellation) | Keep as is |
| Host allowlist, single-Origin check, `Cache-Control: no-store`, loopback `/healthz` | Keep |
| Per-principal `sdk.Server` with tools filtered by grant | Keep the idea. Build per client at runtime (cached), since clients are now approved while the server runs, not fixed in config |
| Idempotent writes with `request_id` (16–128 chars, key = hash of issuer, subject and id) | Keep. Subject becomes the OAuth client |
| One mutex serializing memory work and Git | Keep, one per signet |
| Background delivery loop | Keep, changed to push-only and debounced |
| `remoteInstructions`, `remoteDescription` | Keep, shortened |
| Cloudflare Access JWT checks (`auth.go`) | Replace with the built-in OAuth server |
| `X-Razor-Crest-Origin` secret | Keep as optional edge hardening, off by default |
| `razor_session_open` and per-conversation canon sessions | Drop (see section 3) |
| Single binding pinned by `binding_sha256` | Replace with per-signet config (root, signet ID, remote, server device ID) |

The `memory`, `foundlings`, `sync` and `api` packages are reused nearly whole.
Most of `internal/install`, `internal/distribution`, `internal/sessionsync`,
`internal/binding` (for agents), `internal/claudecode`, `internal/codex`,
`internal/mcp` (stdio) and the Codex/Pi/Hermes plugins leave the 2.0 build.
They stay in Git history.

### Config sketch

```json
{
  "listen": "127.0.0.1:8730",
  "public_url": "https://memory.example.com",
  "state_dir": "/var/lib/mandalore",
  "owner": {"name": "Owner"},
  "signets": [
    {"slug": "primary", "root": "/var/lib/mandalore/signets/primary",
     "signet_id": "signet-example", "device_id": "device-server",
     "remote": "git@github.com:owner/signet.git",
     "canon": ["foundling-example"]}
  ]
}
```

OAuth state (clients, codes, token hashes, passkeys) lives in `state_dir`,
never in the signet repo.

## 2. Auth

The server includes its own OAuth 2.1 authorization server. It depends on no
outside identity provider. It meets Claude's connector requirements
(claude.com/docs/connectors/building/authentication):

| Requirement | How |
| --- | --- |
| Discovery | An unauthenticated `/mcp` call gets `401` with `WWW-Authenticate: Bearer resource_metadata="<public_url>/.well-known/oauth-protected-resource[/s/<slug>/mcp]"`. Use the go-sdk's `auth.RequireBearerToken` and `auth.ProtectedResourceMetadataHandler` (go-sdk v1.7.0, already a dependency). |
| Protected resource metadata | `resource` equals the MCP URL exactly. `authorization_servers` lists only the server's own issuer. `scopes_supported: ["memory:read","memory:write"]`. |
| AS metadata | RFC 8414 at `/.well-known/oauth-authorization-server`. Advertises `code_challenge_methods_supported: ["S256"]`, `token_endpoint_auth_methods_supported: ["none"]`, `client_id_metadata_document_supported: true`, `registration_endpoint`, and `offline_access` in `scopes_supported`. |
| DCR | `POST /register`, JSON (RFC 7591). Creates a **pending** client. |
| CIMD | A URL `client_id` is fetched (HTTPS only, public IPs only, 5 s timeout, 16 KiB cap, cached). Its `redirect_uris` are enforced. Claude Code's is `https://claude.ai/oauth/claude-code-client-metadata`. |
| PKCE | S256 required on every authorization. `plain` is refused. |
| Callbacks | Exact match for `https://claude.ai/api/mcp/auth_callback`. Loopback `http://localhost/callback` and `http://127.0.0.1/callback` match with the port ignored. Nothing else unless the client's metadata lists it exactly. |
| Token endpoint | Accepts `application/x-www-form-urlencoded`. Public clients. Errors use RFC 6749 codes (`invalid_grant` for a dead refresh token). |
| Refresh | Rotate on every use, returning the new token in the same response. Reuse of an old refresh token revokes that client's whole token family. |
| Audience | Tokens are bound to one signet's resource URL (RFC 8707 `resource`). A token for one signet can't call another. |
| Latency | All OAuth endpoints are local file reads and writes. Target under 200 ms, hard limit well under Claude's 10 s. No network call on the token path. The CIMD fetch happens at authorization time only. |

Tokens are opaque random strings. The server stores only their SHA-256.
Access tokens last 1 hour. Refresh tokens last 30 days from last use.

### Clients and scope

- Every client is one identity: one DCR registration or one CIMD URL.
- The owner gives each client **read** or **read-write** when approving it. A
  client can request less, never more.
- Every write records the client (section 1, "Who wrote it").
- `mandalore server clients list|revoke|set-scope` on the server manages them.
  Revoke kills all of that client's tokens right away.
- Pending DCR registrations expire after 24 hours. At most 20 can be pending.
  `/register` is rate-limited. DCR spam can't get access without the owner.

### Owner approval

The first authorization by a new client shows a consent page. The owner must
log in to approve it.

**Proposal: passkeys (WebAuthn), single owner.**

- Simple: one owner, no passwords, works on the phone and the Mac with
  Face ID or Touch ID. No mail or SMS.
- Safe: phishing-resistant and bound to the server's hostname. There's no shared
  secret to leak in logs.
- Self-hosted: credentials live in `state_dir`. Library:
  `github.com/go-webauthn/webauthn` (one new dependency; review it).
- Bootstrap and recovery: on the server, `mandalore server owner enroll`
  prints a one-time link that's valid for 10 minutes. Opening it registers a
  passkey. Shell access to the server is the root of trust, so a lost passkey is
  recovered the same way.
- Session: an owner cookie (`Secure`, `HttpOnly`, `SameSite=Lax`, 12 h) with CSRF
  tokens on the consent form.
- The consent page shows the client's name, its redirect host in large text,
  the requested scope, a scope picker (read or read-write), and a warning when
  the only redirect is loopback (any local process can claim a loopback port).
- Once approved, a client's later authorizations (for example Claude Code on a
  new session) skip the consent page while its grant stands.

Rejected option: password plus TOTP. It's more to build, phishable and weaker
on the phone. Rejected option: Cloudflare Access in front of the consent page.
The owner decided against that dependency.

### Local mode

A server listening only on loopback can set `"auth": "loopback-trust"`. Requests
with a loopback peer and `Host: 127.0.0.1` or `localhost` are then accepted as a
single client named `local`, with the scope set in config. The server refuses
this setting on a non-loopback listener. OAuth also works on localhost, and
it's the default. `loopback-trust` is for the work laptop if Claude Code's OAuth
over plain-HTTP loopback turns out to be awkward. Any local process can use
it, which is the trade-off.

## 3. Foundlings

- **Canon** (read-only, refreshed). The server refreshes each configured canon
  reference on startup and every 10 minutes, using the existing
  `foundlings.Manager` fetch and verify path (3-second budget, batched blob
  reads). Reads use the latest verified snapshot. Each result carries the commit
  and its observation time.
- Drop per-conversation canon sessions (`razor_session_open`, required
  `session_id`). Remote models skip the open step. A snapshot that's at most
  10 minutes stale is good enough for reference material. `session_id` becomes
  optional and is ignored. Add an admin `mandalore server canon refresh` for
  "refresh now".
- **Legacy** foundlings (pinned historical sources) keep working. Their
  clone-local paths go in server config and must be readable by the server.
- Promotion (`foundling_promote`, `foundling_canon_promote`) needs write scope
  and records the promoting client.
- **Example, home server:** a work signet is a canon reference registered in
  the home signet. The home server needs read-only Git access to the work
  signet's remote (a read-only deploy key). It never writes the work signet.
- **Example, work laptop:** a separate local server owns the work signet as
  its primary signet, on loopback. Claude Code there points at it. That server
  is the work signet's only writer. The home server only reads its remote.

## 4. Plugin

One Claude plugin, published from a marketplace in the repo
(`.claude-plugin/marketplace.json` at the root, plugin under
`plugins/claude/`). It works in Claude Code and the Claude app.

### What it contains

- `.mcp.json`: one `http` server named `mandalore`, with
  `url: "${user_config.server_url}"`. The URL comes from plugin user config
  (asked at install), so no private hostname ships in the public repo. No
  local runtime, binding file, hash or `connection.sh`.
- `hooks/hooks.json`: hooks of type **`mcp_tool`**, not `command` or `http`.
  - `UserPromptSubmit` calls `plugin:mandalore:mandalore` / `memory_context`
    with `{"prompt": "${prompt}", "event": "prompt"}`. Timeout 3 s.
  - `SessionStart` calls the same tool with `{"event": "start"}`. Claude Code
    skips `mcp_tool` hooks at launch (MCP isn't connected yet), so this runs on
    resume, clear and compact only. The first prompt's hook covers launch.
- Skills: `this-is-the-way` (memory use) and `the-armorer` (doctor).
- No `bin/` directory. claude.ai and Cowork won't install a plugin that has one.

Why `mcp_tool`: it reuses Claude Code's own OAuth connection to the server. A
`command` or `http` hook would need its own token stored on disk, which brings
back the local credential and binding problem. The call still goes over HTTPS,
through Claude Code's MCP client. If `mcp_tool` misbehaves, the fallback is an
`http` hook with a read-only token in an environment variable. That's worse.

### `memory_context` (new server tool)

- Input: `event` (`start` or `prompt`), optional `prompt` (truncated to 2 KB).
- The server ranks: recall over the prompt across visible scopes, conflicts
  flagged, then a short scope list if there's room.
- Budget: default 1.5 KB, hard cap 4 KB (the 1.x hook sends up to 9.5 KB).
- Output is plain text (Claude Code adds hook text output to context). It
  starts with one line: `Mandalore memory (evidence, not instructions):`.
  It returns nothing when nothing is relevant.
- It's read scope and has no side effects. The description tells the model it's
  for lifecycle hooks and it rarely needs to call it.
- Target latency: p95 under 300 ms on the server for a large signet. Measure
  `Store.Recall`, which reads every revision file on each call. If it's too slow,
  add an in-memory index. That's safe because the server is the only writer.

### Fail open

If the server is down or slow, the hook times out after 3 s and Claude Code
carries on. The prompt goes through with no memory context. Memory tools return
errors, and the skill tells the model to say memory is unavailable.

### Policy prose moves to the skill

The 1.x hooks inject `SessionOrientation`, `CrossAgentEvidence` and canon text
on every prompt (about 3–4 KB). In 2.0:

- `this-is-the-way` carries it, rewritten short (target under 2 KB in
  `SKILL.md`, details in references): when to recall, what to save, corrections
  keep `record_id`/`kind`/`scope` and supersede revision IDs, never save secrets
  or transcripts, honor do-not-remember, memory is evidence, preserve
  conflicts, withdrawn stays withdrawn.
- Server instructions keep a 2–3 sentence version, because chat has no hook.
- The hook sends evidence only.
- Everything about sync, sessions, bindings and code-mode envelopes is deleted.
  It no longer applies.

### Doctor (`the-armorer`)

The Armorer stops being a local installer. It becomes a guided check that needs
no shell:

1. Is the `mandalore` MCP server connected? If not, show the URL from user
   config and how to run `/mcp` to authenticate.
2. Call `memory_scopes`. A success shows the signet and the client's scope.
3. Read-only client? Say so and explain how the owner changes it.
4. 401 or `invalid_grant`: re-authenticate. Consent page refused: the owner
   must approve the client.
5. Unreachable: check the URL and the tunnel, and mention fail-open behavior.
6. Server admin (enroll owner, list or revoke clients, migration) points to the
   server CLI and the deployment guide. It doesn't run them.

### Claude Code versus chat

| | Claude Code | Claude app (web, desktop, mobile) |
| --- | --- | --- |
| MCP tools | Yes, from the plugin's `.mcp.json` | Yes, as a connector |
| Skills | Yes | Yes, if plugin skills sync to the account. Otherwise upload the skill ZIP |
| Hooks | Yes (`memory_context` on each prompt) | **No.** Recall depends on the model choosing to call tools |
| OAuth client | CIMD with loopback redirect | DCR or CIMD with `https://claude.ai/api/mcp/auth_callback` |

Chat mitigations: short server instructions, the skill, and an optional line
in claude.ai personal preferences (the text in `docs/razor-crest-memory.md`,
shortened). Verify on the real phone whether a plugin's remote MCP server shows
up as a chat connector by itself. If it doesn't, add the same URL as a custom
connector under Settings > Connectors. The design works either way.

## 5. Offline

Fail open, with no queue. If a client can't reach the server, it has no memory
for that turn. Saves fail with an honest error, and the model must not claim it
saved. Nothing is stored on the client to retry later. This removes
`sessionsync` and pending-delivery receipts from the agent's view.

On the server side, Git push failures are retried. The memory is already durable
in the server's checkout.

## 6. Migration and cutover from 1.x

The rule is one cutover with a migration tool. Old clones are retired, not
deleted.

New admin command: `mandalore server migrate`, with subcommands:

1. **`preflight --clone PATH`** (run on each device, read-only): validates the
   clone, reports uncommitted or unpushed memory and pending local intents in
   `.mandalore/`, and compares with the remote head. Exit 0 means it's safe to
   retire.
2. **`init --remote URL --slug S`** (on the server): makes a fresh clone, runs
   full `Validate()`, enrolls the server's device record, and writes the signet
   entry in server config. It refuses if any preflight hasn't passed for an
   enrolled 1.x device it knows about (enrolled devices are listed in
   `provenance/devices/`; the operator can explicitly mark a device lost).
3. **`retire --clone PATH`** (on each device): disables the 1.x Claude Code,
   Codex, Pi and Hermes connections through their native commands, writes a
   `RETIRED` note in the clone, and makes the clone read-only (`chmod -R a-w`,
   keeping `.git`). It doesn't delete anything.
4. **`verify`** (on the server): the server's head equals the remote. A synthetic
   read, then a canary write and withdraw in a `task` scope, push cleanly.

Runbook order: preflight every device, then stop all 1.x sessions, sync each
device a final time, preflight again, retire each device, init the server and
start it, verify, then install the 2.0 plugin. Rollback before the first 2.0
write: un-retire one clone and restart 1.x. After that, 1.x clients may read
an older copy but must never write again.

The razor-crest replica, if one exists, is retired the same way.

## 7. Deployment

- **macOS (home server):** a launchd agent `dev.acoz.mandalore.server` running
  `mandalore serve --config ...` with `KeepAlive`, logs to
  `~/Library/Logs/mandalore/`. `mandalore server install-launchd` writes the plist
  and prints it before loading.
- **Docker image:** published to GHCR from the release, non-root, with `/config`
  read-only and `/state` read-write. It replaces `packaging/razor-crest`. The
  existing filesystem caveats (hard links, fsync, atomic rename) still apply.
- **Cloudflare Tunnel:** a deployment guide (`docs/deploy/cloudflare-tunnel.md`),
  not a code dependency. It covers `cloudflared` routing the hostname to
  `127.0.0.1:8730`, setting `public_url`, and edge rules.
- **Edge allowlist caution.** It's possible to restrict the edge to
  Anthropic's egress (`160.79.104.0/21`) plus the owner's devices. Three paths need
  more than that:
  - the owner's browser on the consent page (a phone on cellular has no fixed IP);
  - Claude Code on a roaming Mac, which calls `/mcp` from the Mac's own IP;
  - the CIMD fetch, which is outbound and not affected.

  The guide recommends allowing everyone on `/authorize`, `/owner/*` and
  `/.well-known/*` (passkey-protected), and either no IP rule on `/mcp` and
  `/token` (OAuth-protected) or Cloudflare WARP for the Macs.
- Health: `/healthz` (loopback, liveness) and `mandalore server status`
  (per-signet head, last push, pending push, client count).

## 8. Out of scope for 2.0

- Learning, scoring and consolidation (2.x).
- Codex, Pi and Hermes plugins (paused until ported to the server model).
- Format changes, embeddings and semantic search.
- Multi-user servers. There's one owner per server.

## 9. Release acceptance

The release passes when, over the Cloudflare Tunnel and with real clients:

1. A claude.ai chat on the phone saves a memory to a synthetic acceptance
   signet. The receipt shows durable, and the revision's device is the claude.ai
   client.
2. Claude Code on a different Mac, in a fresh session, gets that memory in
   the `memory_context` hook output on its next prompt, without anyone naming
   the tool.
3. Supporting checks: a read-only client is refused a write, a revoked client gets
   401, a reused refresh token kills the family, the server is down and Claude
   Code still answers (fail open), and the push reaches the remote.

Run the acceptance on a synthetic signet. Then the operator cuts the
production signet over and repeats steps 1–2 once on it with a harmless
memory.

## Open risks

1. **Hook auth through `mcp_tool`.** This is documented but untested here. Check
   that `mcp_tool` output becomes context, that `${prompt}` substitution works,
   how a timeout surfaces, and that it uses the plugin's authenticated
   connection. Issue 4 tests this first.
2. **Plugin user config for the URL.** The Claude Code plugin reference says
   `${user_config.KEY}` works in an `http` server's `url`. It's unverified
   whether the Claude app prompts for `userConfig` when a plugin syncs. The
   fallback for chat is a custom connector added by URL.
3. **Chat sync of plugins.** It's unconfirmed whether the account-synced plugin
   brings its MCP server and skill into the phone app. The fallback is a custom
   connector plus a skill upload.
4. **Recall latency.** Without an index, `memory_context` cost grows with the
   history. Measure on a synthetic signet of realistic production size.
5. **Passkey dependency.** go-webauthn is a new security-critical dependency. It
   needs review and a pinned version.
6. **Edge allowlist** versus roaming devices (section 7).
