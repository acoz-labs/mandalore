# Solution Decision

## Decision Drivers

Useful before setup; no execution or product writes by default; truthful evidence
scope; shared UI/agent semantics; no new private-data or release authority.

## Competing Approaches

1. Run existing Armorer and decorate its result. Reuses deep checks but cannot
   meet the measured no-execution/no-native-write default.
2. Add static tables alone. Cheap but fails the current-machine outcome.
3. Add a small shared assessor plus reviewed declarations and explicit deeper
   handoff. Selected; reuse safe install metadata validation seams.
4. Add external compatibility registry and agentic auto-repair. Excluded scope,
   with unnecessary network, lifecycle and trust boundaries.

## Adversarial Comparison

An executable path does not prove usability; a shim hash does not identify its
interpreter or target. A healthy retained receipt does not prove registration or
active session loading. Identical version labels can represent different source
and artifact bytes. A passing old native scenario cannot certify this invocation.
Static checks must survive these cases by narrowing their claim, not guessing.

## Selected Approach

One shared non-executing assessor with fixed bounded observations and stable
reason codes. Supply built-in versioned declarations; match exact component and
scenario evidence where identifiers are available. Omit automatic online lookup.
Keep the existing deeper inspector as an explicit optional next action.

## Decisions Ledger

| Decision | Rationale |
| --- | --- |
| No subprocesses in default assessment | Native inspection has measured file effects |
| Independent support/setup/evidence dimensions | A single green status would overstate readiness |
| Report unknown dependencies/version indirection | Presence and reported labels are not verification |
| No remembered-content reads | Machine setup does not require personal knowledge |
| Optional prompt from typed findings only | Avoid copying raw metadata into agent instructions |
| No automatic native selection scan | Multiple retained generations need explicit ownership/selection |

The [technical contract](03-design.md) resolves selection and safe defaults:
shared non-executing defaults for paths, no implicit retained generation, receipt
ownership checks before following paths and separate toolkit/retained identities.
Confidence is high in the boundaries and source seams. Native menu quality and
actual implementation behavior remain verification requirements, not assumptions
that authorize completion.
