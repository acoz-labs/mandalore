# Mandalore 2.1.2

[Release 2.1.2](https://github.com/acoz-labs/mandalore/releases/tag/v2.1.2)
makes `memory_remember` say which input to fix. A summary, body or reason over
its limit, and other input refused before anything is written, now return
`input.invalid` with `write_may_have_occurred` false, instead of a
`save.incomplete` that invited retrying input that could never succeed.

**The Claude plugin stays at 2.1.1, on purpose.** Nothing in it changes: its
guidance names neither the limits nor the error codes, and the limits reach
Claude through the server's tool schema. A 2.1.2 server beside a 2.1.1 plugin
is not a missed bump, and merging this change rolls nothing out to installed
plugins ([#229](https://github.com/acoz-labs/mandalore/issues/229)).

2.1.2 changes no OAuth state version, no signet format, no state file and no
configuration, and adds no public HTTP or OAuth path.

Source: `6bd254bfd37d09ece222e6e28991304c044bd0ab`, the merge of
implementation [#244](https://github.com/acoz-labs/mandalore/pull/244) for
#243, which also carries the release preparation. Its tree is identical to
the reviewed head `1a3e7a1`. Identity:

## What changed

- **Input errors are `input.invalid`**
  ([#243](https://github.com/acoz-labs/mandalore/issues/243)). The message
  names the field, its limit in UTF-8 bytes and the size received, for
  example `summary is 363 bytes; the limit is 256 UTF-8 bytes`, and never
  repeats the input text. The same applies to a blank `basis`, an unknown
  `kind`, `sensitivity`, `volatility` or `confidence`, a bad scope, a
  `record_id` without `supersedes` or the reverse, more than 32 `supersedes`,
  a correction that doesn't fit the record's history, and
  `memory_journal_append`'s kind and summary limits. Nothing is stored, so a
  retry with the same `request_id` and corrected input saves.
- **Stale corrections are `memory.stale_heads`.** On a format 2 signet, a
  correction whose `supersedes` aren't the record's current heads returns the
  code the visibility tools already use, again with nothing written. The
  [save errors](../server.md#tools) table lists each correction case by
  format.
- **The tool schemas state the limits.** `memory_remember`'s summary, body and
  reason, and `memory_journal_append`'s kind and summary, carry `minLength` 1
  and `maxLength` set to the byte limit. `maxLength` counts characters, and
  the descriptions say that non-ASCII text can be refused below it.
- **The CLI** (`mandalore memory remember`) gives the same field messages,
  still with exit code 2 for `input.invalid`. A stale correction on a format 2
  signet now returns `memory.stale_heads`, so its exit code changes from 2
  (2.1.1's generic `input.invalid`) to 1.

`save.incomplete` is unchanged, with the same message and fields, for every
failure that can follow a write. The error envelope keeps its shape, and
`memory_remember` already returned `input.invalid` for malformed arguments, so
existing clients need no change.

## Upgrading

Upgrade the server as [2.1.0's notes](2.1.0.md#upgrading-a-running-launchd-server)
describe, using 2.1.2 in place of 2.1.0. No signet or state changes, and
nothing on the client needs to change.

## Recovery

Previous artifact: [2.1.1](2.1.1.md). Rolling the server back to 2.1.1 changes
no data: records saved by 2.1.2 read the same. Clients then see
`save.incomplete` again for over-limit input.

The independent maintainer reviewed #244 and
[approved](https://github.com/acoz-labs/mandalore/pull/244#pullrequestreview-5790311448)
it in round 1 with three low findings. After those were fixed, the maintainer
[approved](https://github.com/acoz-labs/mandalore/pull/244#pullrequestreview-5790491474)
it at exactly `1a3e7a1`

then [nominated](https://github.com/acoz-labs/mandalore/issues/243#issuecomment-6666785607)
and [accepted](https://github.com/acoz-labs/mandalore/issues/243#issuecomment-6666842287)
([receipt](https://github.com/acoz-labs/mandalore/issues/243#issuecomment-6666931440))
the retained candidate
`mandalore:6bd254bfd37d09ece222e6e28991304c044bd0ab:sha256:6cc86586decbf643c08b07a169776a09bf9c930ee412d03f178888ed09b39aba`.
The merge commit `6bd254b`'s tree is identical to `1a3e7a1`'s (`9b0c5119…`).
Acceptance used synthetic state only, with a temporary `HOME`; the old side
was the published, checksum-verified 2.1.1.

- **Retained distribution:** `bin/build-artifacts` at `6bd254b`, in a clean
  worktree, gave the seven files for 2.1.2, and `SHA256SUMS` verifies them.
  `install.sh` is byte-identical to 2.1.1's, and the darwin/arm64 binary
  passes `codesign -v`. `bin/promote-local-candidate --verify-only` passed for
  that identity and refused a copy with one byte appended.
- **Issue criteria (#243):** the published 2.1.1 and the retained 2.1.2 each
  served fresh synthetic signets behind a loopback server, on format 1 and
  format 2, and got the same MCP calls.
  - The issue's 363-byte summary, sent twice, gave `save.incomplete` with
    `write_may_have_occurred` true on 2.1.1, and on 2.1.2 `input.invalid`
    "summary is 363 bytes; the limit is 256 UTF-8 bytes; nothing was saved."
    with `write_may_have_occurred` false.
  - A 258-byte multibyte summary, a blank `basis`, a 4097-byte journal summary
    and a correction that changes `kind` went from `save.incomplete` to
    `input.invalid`.
  - A correction against a superseded head was saved as a visible fork on
    format 1 by both versions. On format 2 it went from `save.incomplete` to
    `memory.stale_heads`, with `write_may_have_occurred` false.
  - Refused calls wrote nothing: the signet's record, source and intent file
    count didn't change. The same `request_id` with a 256-byte summary then
    saved durably.
  - `tools/list` shows `maxLength` 256 and `minLength` 1 on `record.summary`,
    with the bytes-versus-characters note; 2.1.1 shows no limits. The CLI
    exits 2 with the field message for the 363-byte summary.
  - A real mid-write failure staying `save.incomplete` was proved by the test
    in the candidate's `bin/ci`, not by a live probe.
- **Native runtime and plugin:** the darwin/arm64 binary ran natively
  (`version`, `signet create`, `bind`, `memory remember`, `checkpoint`, the
  signet upgrade, `serve`, MCP `tools/list` and `tools/call`, `release plan`
  and `apply`). Claude Code 2.1.318, fully isolated with a temporary `HOME`
  and `CLAUDE_CONFIG_DIR`, no token and no keychain link, installed plugin
  2.1.1 from the merge's marketplace, and its MCP server connected to the
  2.1.2 server. The check reports installation and connection, not a model
  turn.
- **Upgrade, rollback and re-upgrade:** 2.1.1 → 2.1.2 → 2.1.1 → 2.1.2,
  - through the launcher, from the published 2.1.1 to the candidate, then
    `--retained 20c766e0…` and `--retained 6cc86586…`, each reporting the
    expected version;
  - as a bare binary, with the atomic swap, after which the swapped 2.1.2
    served and returned `input.invalid` for the 363-byte summary.

  A fresh install into an empty prefix gave 2.1.2 at `6bd254b`, byte-identical
  to the accepted binary, and a launcher without a Mandalore ownership receipt
  was refused and left untouched.

[Publication](https://github.com/acoz-labs/mandalore/issues/243#issuecomment-6667116897)
([release record](https://github.com/acoz-labs/mandalore/issues/243#issuecomment-6667128268))

- **Same bytes:** `bin/release-publication verify` passes for this identity,
  with seven assets. All seven, downloaded fresh, are byte-identical to the
  accepted candidate, `SHA256SUMS` passes, and `manifest.json` hashes to
  `6cc86586…`. The darwin/arm64 binary (`ddc8ec8f…`) reports 2.1.2 at

- **The issue's case on the published binary:** on fresh synthetic signets, on
  format 1 and format 2, it gave the same results as acceptance, including
  `input.invalid` for the 363-byte summary and `memory.stale_heads` for a

Out of scope: darwin/amd64, linux/amd64 and linux/arm64 weren't run natively
(cross-builds aren't native acceptance), the live `launchctl kickstart -k`
step of the bare-binary upgrade wasn't exercised, and no container image is
published. A release is not proof that any machine updated. The plugin is
unchanged at 2.1.1, so nothing reached plugin installations
([#229](https://github.com/acoz-labs/mandalore/issues/229)).
