# Mandalore 2.4.0

Release 2.4.0 records which client wrote each memory. A write from Claude Code
now records the harness `Claude Code (document on claude.ai)` instead of
`claude.ai`, so it no longer looks the same as a write from the claude.ai app.
Writes over the older MCP protocols also record their transport session. This
is a server release; the Claude plugin stays at 2.3.0.

Nothing existing is rewritten. Records, journal entries, scope labels and moves
written before 2.4.0 keep the authorship they have. There is no signet format
change: the release fills the existing `harness` and `session_id` fields, which
every release since 2.1.2 reads.

2.4.0 changes no OAuth state version, no signet manifest version, no state
file and no configuration. It adds a response header but no public HTTP or
OAuth path, so the Cloudflare path allowlist needs no change. It needs no new
secret.

container image: build from packaging/server; published image to follow.
([#188](https://github.com/acoz-labs/mandalore/issues/188); see
[Docker](../server.md#docker).)

## What changed

- **The harness names the client**
  ([#249](https://github.com/acoz-labs/mandalore/issues/249); see
  [Who wrote it](../server.md#who-wrote-it)).
  - An OAuth client's writes record `<client name> (document on <host>)` for a
    metadata-document client, such as Claude Code, or `<client name> (redirect
    to <host>)` for a client registered with a redirect, such as a hosted app.
    The name comes from the client's registration, and the host is the one
    that serves its document or redirect. A local client still records
    `local`.
  - Both parts keep only printable characters, and the value is at most 128
    bytes.
  - Device labels and `server clients list` are unchanged.
- **`session_id` records the MCP transport session, where there is one.**
  - On MCP protocols up to `2025-11-25`, which open with `initialize`, the
    server gives each connection a random `Mcp-Session-Id`, and that
    connection's writes record it.
  - On the sessionless protocol `2026-07-28`, which Claude Code uses, writes
    record `null` as before.
  - The ID labels one connection. It is not an agent or Claude Code session,
    holds no secret, and is never checked: the server keeps no session table,
    so a restart ends no session.
  - Session identity on sessionless MCP is
    [#258](https://github.com/acoz-labs/mandalore/issues/258).
- **Retries.** A `request_id` retry from a new connection returns the first
  receipt, as before: the session ID is not part of the request's
  idempotency check.
- `memory_history`, `memory_journal` and `memory_prime` return the new values
  where they already return authorship. There is no new tool.
- **Prime can hold one fewer item.** Authorship is longer, and
  `memory_prime` packs whole items into a byte budget (8192 bytes by
  default). A journal entry written by an OAuth client from 2.4.0 carries a
  longer harness: 26 more bytes for Claude Code's. It carries 24 more bytes
  when a session ID is set. So in a scope that already fills the default
  budget, prime can leave out an item that fitted on 2.3.0. Prime drops whole
  items from the oldest end, as before. The item is still there: a larger
  `budget_bytes`, recall or `memory_journal` returns it.

Anything that matches `harness == "claude.ai"` to find Claude Code's or the
claude.ai app's writes needs the new values for writes from 2.4.0 on; earlier
writes keep `claude.ai`.

## Upgrading

Upgrade the server as [2.1.0's notes](2.1.0.md#upgrading-a-running-launchd-server)
describe, using 2.4.0 in place of 2.1.0. Other servers or clones that sync the
same signet can upgrade in any order: every release since 2.1.2 reads 2.4.0's
writes. There are no signet or state changes.

One retry case changes at the upgrade. Suppose 2.3.0 accepted a write but the
client never got its receipt, and the client retries it with the same
`request_id` after the upgrade. The retry now records a different harness, so
it returns `request.conflict` and writes nothing. The first write may or may
not be saved. 2.3.0 may have published it before the receipt was lost. Or it
may have stopped after recording the request but before publishing, and
2.4.0 never finishes that write. Check with `memory_history`, or recall, and
save it again under a new `request_id` only if it isn't there.

The plugin's only change is README wording, worded for server 2.4.0 and
later. It reaches installations when this release's PR merges
([#229](https://github.com/acoz-labs/mandalore/issues/229)) and changes no
behaviour on 2.3.0.

## Recovery

Previous artifact: [2.3.0](2.3.0.md). Rolling back changes no existing data.
Writes made by 2.4.0 keep their harness and session values, and 2.3.0 reads
them, because the fields and their validation are the same. New writes go
back to the host harness and a `null` session.

## Evidence and scope

The independent maintainer reviewed
[#256](https://github.com/acoz-labs/mandalore/pull/256) in two code rounds.
Round 1
[approved](https://github.com/acoz-labs/mandalore/pull/256#pullrequestreview-5861578777)
`e0d6ad1` with two lows in these notes: a retry across the upgrade may find
its first write unpublished, and prime can drop an item at the budget edge.
The fix moved the head, so round 2
[approved](https://github.com/acoz-labs/mandalore/pull/256#pullrequestreview-5861750006)
exactly `d8aa13f`
([pre-merge receipt](https://github.com/acoz-labs/mandalore/pull/256#issuecomment-6800891562),
[post-merge verification](https://github.com/acoz-labs/mandalore/pull/256#issuecomment-6801078508)).
In round 1 the reviewer also had the 2.3.0, 2.2.1 and 2.1.2 memory code
validate and read a record and a journal entry with a 128-byte harness and a
set `session_id`. The plan, `docs/changes/249-authorship/plan.md`, passed two
plan-review rounds first. Before any code, a
[probe](https://github.com/acoz-labs/mandalore/pull/256#issuecomment-6799807563)
found that Claude Code 2.1.322 uses sessionless MCP `2026-07-28`. That led to
the requester's
[ruling](https://github.com/acoz-labs/mandalore/issues/249#issuecomment-6799835409):
`session_id` is set only where the transport has a session. A later
[ruling](https://github.com/acoz-labs/mandalore/issues/249#issuecomment-6800628869)
accepted prime's drop at the budget edge.

The maintainer then
[nominated](https://github.com/acoz-labs/mandalore/issues/249#issuecomment-6801184686)
and [accepted](https://github.com/acoz-labs/mandalore/issues/249#issuecomment-6801255359)
([receipt](https://github.com/acoz-labs/mandalore/issues/249#issuecomment-6801347089))
the retained candidate built from `fd024a2`. `bin/sdlc audit --before
36ec6a3 --sha fd024a2` passed. Acceptance used synthetic state only, with a
temporary `HOME`. The old side was the published, checksum-verified 2.3.0
(manifest `f99baab0…`).

- **Issue criteria (#249, as amended):** the retained darwin/arm64 binary
  served a synthetic format 2 signet with `loopback-trust`.
  - Two raw `initialize` connections on `2025-11-25` were each issued a
    different 26-character `Mcp-Session-Id`. Their records and journal
    entries record it, `memory_history` and `memory_journal` return it, and
    all four writes carry one device ID.
  - A default Go SDK client on `2026-07-28` saved with `session_id: null`, as
    did a raw `2026-07-28` write carrying a stray `Mcp-Session-Id`. Both
    writes succeeded.
  - The harness on the client's own writes, old authorship byte for byte,
    and sanitising and bounds are covered by the tests at `fd024a2`. They
    include an in-process OAuth flow that records
    `<name> (document on <host>)` and `<name> (redirect to <host>)`.
  - `bin/ci` passed on the merge commit. `govulncheck` v1.9.0 at `fd024a2`
    reports no reachable vulnerability, and binary mode is clean on all four
    binaries.
- **Requester's eval:** the requester ran a private eval of recall, prime
  and history before publication; it isn't part of this record.
- **Retained distribution:** `bin/build-artifacts` at `fd024a2`, in a clean
  worktree, gave the seven files for 2.4.0 with Go 1.26.11. `SHA256SUMS`
  verifies them, and a second build was identical. `install.sh` is
  byte-identical to 2.3.0's. The darwin/arm64 binary (`2084bf0d…`) passes
  `codesign -v`. `bin/promote-local-candidate --verify-only` passed for that
  identity and refused a copy with one byte appended.
- **Native runtime and plugin:** the darwin/arm64 binary reports 2.4.0 at
  `fd024a2`. Claude Code 2.1.322 ran fully isolated, with a temporary `HOME`
  and `CLAUDE_CONFIG_DIR`, no token and no keychain link. It installed the
  plugin, still 2.3.0, from the merge's checkout and connected to the
  candidate server. The plugin's hooks, `.mcp.json` and `plugin.json` are
  byte-identical to the merge's, and the real Claude Code configuration was
  unchanged.
- **Upgrade, rollback and re-upgrade:** 2.3.0 → 2.4.0 → 2.3.0 → 2.4.0.
  - Through the launcher: from the published 2.3.0 to the candidate, then
    `--retained f99baab0…` and `--retained 43f7c89f…`, each reporting the
    expected version, with the installed runtime byte-identical to the
    candidate.
  - As a bare binary, with the atomic swap, each step reporting the expected
    version.

  A fresh install into an empty prefix gave 2.4.0 at `fd024a2`, and a
  launcher without a Mandalore ownership receipt was refused and left
  untouched.

[Publication](https://github.com/acoz-labs/mandalore/issues/249#issuecomment-6801448417)
([release record](https://github.com/acoz-labs/mandalore/issues/249#issuecomment-6801463198))

- **Same bytes:** `bin/release-publication verify` passes for this identity
  with seven assets. All seven, downloaded fresh, are byte-identical to the
  accepted candidate, `SHA256SUMS` passes, and `manifest.json` hashes to
  `43f7c89f…`. The darwin/arm64 binary reports 2.4.0 at `fd024a2` with Go
  1.26.11 and passes `codesign -v`. `gh release verify v2.4.0` passes, and
  `gh release verify-asset` passes for `manifest.json` and that binary.
- **Public installation:** with a temporary `HOME`, from 2.3.0 in the
  default prefix, the published `sh install.sh 2.4.0` gave 2.4.0 at
  `fd024a2` with 2.3.0 retained, and the installed runtime is byte-identical

  nothing. It was rerun from a new temporary `HOME`. Rollback with
  `--retained f99baab0…` and forward again with `--retained 43f7c89f…` both
  applied.
- **Immutable:** v2.4.0 is immutable and not a draft or prerelease, with its
  tag at `fd024a2`. v2.3.0 is unchanged.

Out of scope:
- the new harness on a real OAuth write with the released binary, since
  acceptance used `loopback-trust`. It is covered by tests, and the owner
  checks it on the live server after the upgrade: a Claude Code write should
  record `Claude Code (document on claude.ai)` with `session_id: null`;
- native runs of darwin/amd64, linux/amd64 and linux/arm64 (cross-builds
  aren't native acceptance);
- a Claude Code session driven by a model;
- the live `launchctl kickstart -k` step of the bare-binary upgrade.

No container image is published. A release is not proof that any machine
updated: no live server was upgraded.
