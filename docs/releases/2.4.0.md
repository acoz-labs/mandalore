# Mandalore 2.4.0

Release 2.4.0 records which client wrote each memory. A write from Claude Code
now records the harness `Claude Code (document on claude.ai)` instead of
`claude.ai`, so it no longer looks the same as a write from the claude.ai app.
Writes over the older MCP protocols also record their transport session. This
is a server release; the Claude plugin stays at 2.3.0.

Nothing existing is rewritten. Records, journal entries, scope labels and moves
written before 2.4.0 keep the authorship they have. There is no signet format
change: the release fills the existing `harness` and `session_id` fields, which
every release since 2.1.2 reads.

2.4.0 changes no OAuth state version, no signet manifest version, no state
file and no configuration. It adds a response header but no public HTTP or
OAuth path, so the Cloudflare path allowlist needs no change. It needs no new
secret.

container image: build from packaging/server; published image to follow.
([#188](https://github.com/acoz-labs/mandalore/issues/188); see
[Docker](../server.md#docker).)

## What changed

- **The harness names the client**
  ([#249](https://github.com/acoz-labs/mandalore/issues/249); see
  [Who wrote it](../server.md#who-wrote-it)).
  - An OAuth client's writes record `<client name> (document on <host>)` for a
    metadata-document client, such as Claude Code, or `<client name> (redirect
    to <host>)` for a client registered with a redirect, such as a hosted app.
    The name comes from the client's registration, and the host is the one
    that serves its document or redirect. A local client still records
    `local`.
  - Both parts keep only printable characters, and the value is at most 128
    bytes.
  - Device labels and `server clients list` are unchanged.
- **`session_id` records the MCP transport session, where there is one.**
  - On MCP protocols up to `2025-11-25`, which open with `initialize`, the
    server gives each connection a random `Mcp-Session-Id`, and that
    connection's writes record it.
  - On the sessionless protocol `2026-07-28`, which Claude Code uses, writes
    record `null` as before.
  - The ID labels one connection. It is not an agent or Claude Code session,
    holds no secret, and is never checked: the server keeps no session table,
    so a restart ends no session.
  - Session identity on sessionless MCP is
    [#258](https://github.com/acoz-labs/mandalore/issues/258).
- **Retries.** A `request_id` retry from a new connection returns the first
  receipt, as before: the session ID is not part of the request's
  idempotency check.
- `memory_history`, `memory_journal` and `memory_prime` return the new values
  where they already return authorship. There is no new tool.

Anything that matches `harness == "claude.ai"` to find Claude Code's or the
claude.ai app's writes needs the new values for writes from 2.4.0 on; earlier
writes keep `claude.ai`.

## Upgrading

Upgrade the server as [2.1.0's notes](2.1.0.md#upgrading-a-running-launchd-server)
describe, using 2.4.0 in place of 2.1.0. Other servers or clones that sync the
same signet can upgrade in any order: every release since 2.1.2 reads 2.4.0's
writes. There are no signet or state changes.

One retry case changes at the upgrade. Suppose a write was saved by 2.3.0 but
its receipt was lost, and the client retries it with the same `request_id`
after the upgrade. The retry now records a different harness, so it returns
`request.conflict` and writes nothing. The first write is already saved, so
check for it with `memory_history` before saving it again under a new
`request_id`.

The plugin's only change is README wording, worded for server 2.4.0 and
later. It reaches installations when this release's PR merges
([#229](https://github.com/acoz-labs/mandalore/issues/229)) and changes no
behaviour on 2.3.0.

## Recovery

Previous artifact: [2.3.0](2.3.0.md). Rolling back changes no existing data.
Writes made by 2.4.0 keep their harness and session values, and 2.3.0 reads
them, because the fields and their validation are the same. New writes go
back to the host harness and a `null` session.
