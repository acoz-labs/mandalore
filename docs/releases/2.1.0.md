# Mandalore 2.1.0

[Release 2.1.0](https://github.com/acoz-labs/mandalore/releases/tag/v2.1.0)
makes the Claude plugin's prompt hook selective. `memory_context` injects the
records that answer the prompt, only when something does, and no longer fills
the budget on every prompt. Recall ranks with BM25, so a short, specific
record is no longer outranked by long notes full of common words, for the hook
and for explicit `memory_recall` alike.

2.1.0 changes no OAuth state version, no signet format and no configuration.
Every live token keeps working, and no client needs a new sign-in or consent
because of the upgrade. It adds no public HTTP or OAuth path, so the
[Cloudflare WAF](../deploy/cloudflare-tunnel.md) allow list needs no change.
`serve` takes the same options, including `auth: loopback-trust` and
`local_scope`.

The plugin's hook sends exactly what 2.0.3's did, so a 2.1.0 plugin works
against a 2.0.3 server and the other way round.

Source: `3f7a83fbc6230c4557d21e0cb26a724907dc8751`, the merge of
implementation [#231](https://github.com/acoz-labs/mandalore/pull/231) for
#227, which also carries the release preparation. Its tree is identical to

## What changed

All of it is for [#227](https://github.com/acoz-labs/mandalore/issues/227).
The details are in [Hook selection](../retrieval.md#hook-selection) and
[the server's tools](../server.md#tools).

- **Ranking.** Recall ranks with BM25 over the same field weights as before:
  summary hits count four times a body hit, identifier hits eight times, and
  inflections at a quarter. A term common across the records being searched
  counts for little, and a long record gains little from repeating one.
  Function words such as "what", "is" and "the" still make a record match but
  only break ties. Decisions and preferences rank a little higher than other
  kinds on similar matches. Equal scores order by revision ID.
  `memory_recall` returns the same records in the same shape as before, often
  in a better order.
- **Which prompts get context.** The hook drops function words, words that ask
  for a kind of answer ("answer from context you already have", "don't call
  tools", "in one line") and acknowledgements ("ok", "ready", "thanks, go
  ahead"). A prompt with no term left gets nothing. A record that shares only
  one word with the prompt, and only in its body, is never injected when two
  or more of the prompt's other words go unmatched ("two-factor" in "How do I
  add two-factor login to Django?"), or one does and the shared word is a
  number ("600" in "What is 15 percent of 600?"). A short question such as
  "Are we growing Sungold?" still finds its answer. Otherwise a record is injected
  only if its match covers enough of the prompt's terms, weighted by how rare
  each is, or matches enough rare terms whatever else the prompt says, or has
  a name from the prompt (a word capitalized mid-sentence, such as "Beacon")
  in its summary. Records much weaker than the best match are left out. In
  2.0.3 any shared word injected something.
- **Budget and record count.** The default budget is 2048 bytes, up from
  1536. The top 3 records always appear, each clipped to an even share of the
  budget and marked with `…`, never losing its kind, scope, record ID or
  device. In 2.0.3 a top record whose whole text didn't fit was skipped, and a
  smaller, weaker one was injected instead. Further relevant records follow if
  they fit whole, up to 10 in all. `budget_bytes` still takes 256–4096.
- **Once per session.** `memory_context` takes an optional `session`. Within
  one session it injects each record revision once, again only after the
  record is revised, and lists the scopes once. The server keeps this in
  memory only, per installation, client scope and session, bounded and
  forgotten after 12 hours idle or on restart.

  **Claude Code gets no de-duplication in 2.1.0.** The 2.1.0 plugin doesn't
  send a session yet. A 2.0.3 server refuses unknown input, so a plugin that
  sent `session` would lose all hook context against a 2.0.3 server, during a
  rollback or if the plugin updated before its server. Once servers are on
  2.1.0, the plugin will send `${session_id}`
  ([#228](https://github.com/acoz-labs/mandalore/issues/228)). A native probe
  on Claude Code 2.1.310 found that it substitutes `${session_id}` in an
  `mcp_tool` hook's input, keeps the same ID across `--resume`, gives a new
  session a new one, and turns an unknown `${field}` into an empty string. It
  sends no session header on HTTP MCP calls, so the hook input is the only way
  to pass it.
- **Latency.** On the 250-record evaluation signet, the hook measures about
  12 ms p95 between writes on a development laptop. `bin/ci` asserts 300 ms,
  well under the hook's 3 s timeout, and the hook still fails open.

## Evaluation

A checked-in synthetic set of 250 records runs in `bin/ci`
([method](../retrieval.md#evaluation-set)): 44 questions, each in three
phrasings and inside 15 instruction wrappers, 90 prompts that no record
answers (42 written to collide with the signet's words), 38 short
questions whose answer hinges on one word in a record's body, 24 more
colliding prompts, and a scripted 20-turn session. Every tuning decision used
only the tuning split; the held-out split was computed once, after the code
was frozen. Synthetic results:

| Measure | Split | 2.0.3 | 2.1.0 |
| --- | --- | --- | --- |
| `memory_context` top-1 / top-3 | tuning | 18.4% / 44.8% | 78.9% / 87.4% |
| | held out | 33.3% / 61.9% | 77.3% / 84.6% |
| `memory_recall` top-1 / top-3 | tuning | 22.7% / 37.5% | 77.3% / 93.2% |
| | held out | 11.4% / 29.5% | 75.0% / 88.6% |
| False injection on prompts no record answers | tuning | 71.0% | 14.5% |
| | held out | 67.9% | 14.3% |
| Short questions with the answer in the hook's top 3 | tuning | 25 of 38 | 35 of 38 |
| Colliding prompts that inject | tuning | 23 of 24 | 7 of 24 |
| Injected bytes per prompt over the session | | 1030 | 572 |

These are synthetic results; a real signet's numbers will differ.

### Known deviations

Five of the set's 132 `memory_recall` queries rank their answer lower than
2.0.3 did; 99 rank it higher. They are recorded rather than tuned for. All
are synthetic:

- **`cloud-region` paraphrase**, "Where should new cloud resources be created
  by default?": first → second. The "Cloud account review" note matches one
  more of the question's words ("resources") than the answer does. The answer
  stays in the top 3, and the case's other two phrasings rank it first.
- **`mail-shopping-alias` held-out phrasing**, "Which alias goes on store
  accounts when I sign up?": third → fourth, the one case that leaves the top
  3. Two generic mail notes ("Mail cleanup session" and "Mail provider
  settings") now outrank it by matching "aliases" and "account" through
  inflection, a lexical limit: the answer matches only "alias", since "store"
  and "sign up" aren't its words. The travel-alias decision ranks first, as it
  did in 2.0.3.
- `lanternfish-license` question and paraphrase: first → second, behind the
  decision "Lanternfish's docs are CC BY 4.0, separate from the code license",
  a related licence decision.
- `lanternfish-go-support` held-out phrasing: first → second, behind the
  "Lanternfish contributor guide notes" record, which shares "keep" with the
  question.

## Upgrading a running launchd server

Installing 2.1.0 changes nothing for the process that is already running;
restart it afterwards. First check which executable the agent runs:

```sh
plutil -extract ProgramArguments.0 raw ~/Library/LaunchAgents/dev.acoz.mandalore.server.plist
```

If it shows the launcher, `PREFIX/bin/mandalore`, with `PREFIX/lib/mandalore`
present, follow [A launcher-managed install](#a-launcher-managed-install). If
`PREFIX/bin/mandalore` is a regular file and there is no `PREFIX/lib/mandalore`,
follow [A bare-binary install](#a-bare-binary-install). If it shows a runtime
under `PREFIX/lib/mandalore/releases/`, a CLI install never changes what the
agent runs: after installing, run `server uninstall-launchd`, then `server
install-launchd` again from the launcher.

### A launcher-managed install

1. Install 2.1.0 into the same prefix while the server runs:

   ```sh
   curl -fsSLO https://github.com/acoz-labs/mandalore/releases/download/v2.1.0/install.sh
   sh install.sh 2.1.0
   ```

   or `mandalore release install --version 2.1.0 --prefix PREFIX`. This
   switches the launcher to the 2.1.0 runtime and keeps 2.0.3 retained. The
   running server keeps serving 2.0.3 with the same PID.
2. Restart the agent. Plain `kickstart` does nothing to a running job; `-k`
   stops it first:

   ```sh
   launchctl kickstart -k gui/$(id -u)/dev.acoz.mandalore.server
   ```

3. Confirm 2.1.0 is serving:

   ```sh
   launchctl print gui/$(id -u)/dev.acoz.mandalore.server | grep -E '^\t(state|pid|runs) ='
   lsof -p PID -Fn | grep -m1 '/mandalore$'      # PID from the line above
   mandalore version                              # "version":"2.1.0"
   mandalore server status --config FILE
   ```

   `launchctl print` shows `state = running` with a new PID, and `lsof` names a
   runtime under `releases/sha256-487742c5…/` (2.1.0's manifest), not
   `releases/sha256-84235230…/` (2.0.3's).

To roll back to 2.0.3:

```sh
mandalore release install --retained 84235230c4e6c3a04b23bb187ee3106b288cb2dcd09f5a431b62acdaf5c9ab2a --prefix PREFIX
launchctl kickstart -k gui/$(id -u)/dev.acoz.mandalore.server
```

The mapped runtime is then under `releases/sha256-84235230…/`. Return to 2.1.0
with `sh install.sh 2.1.0`, or its retained runtime under `release install
--retained`, and restart again.

### A bare-binary install

Where the agent runs a release binary copied to `PREFIX/bin/mandalore` by
hand, neither `release install` nor `install.sh` can upgrade it: both refuse
that prefix and change nothing. Swap the binary instead:

1. Download `mandalore_2.1.0_OS_ARCH` and `SHA256SUMS` from the release and
   check the binary with `shasum -a 256 -c --ignore-missing SHA256SUMS`.
2. Keep the old binary and swap in the new one atomically, in the same
   directory, then restart:

   ```sh
   cp -p PREFIX/bin/mandalore PREFIX/bin/mandalore-2.0.3
   cp mandalore_2.1.0_OS_ARCH PREFIX/bin/.mandalore.new && chmod 755 PREFIX/bin/.mandalore.new
   mv -f PREFIX/bin/.mandalore.new PREFIX/bin/mandalore
   launchctl kickstart -k gui/$(id -u)/LABEL
   ```

   The running server keeps serving 2.0.3 until the restart.
3. Confirm as above: a new PID, `PREFIX/bin/mandalore version` reports 2.1.0,
   and `server status` is ok.

To roll back, keep the 2.1.0 binary too, then move the old one back:

```sh
cp -p PREFIX/bin/mandalore PREFIX/bin/mandalore-2.1.0
mv -f PREFIX/bin/mandalore-2.0.3 PREFIX/bin/mandalore
launchctl kickstart -k gui/$(id -u)/LABEL
```

A Docker server is rebuilt from the new tag (`git clone --branch v2.1.0`, see
[Docker](../server.md#docker)) and restarted with the same volumes.

### The plugin

The 2.1.0 plugin changes only its version and README. Installed plugins
track the marketplace on `main`
([#229](https://github.com/acoz-labs/mandalore/issues/229)), so it reaches
installations when this change merges, and `claude plugin update mandalore`
fetches it at once. Its hook input is unchanged, so server and plugin can be
upgraded or rolled back in either order.

## Recovery

Previous artifact: [2.0.3](2.0.3.md) (manifest
`84235230c4e6c3a04b23bb187ee3106b288cb2dcd09f5a431b62acdaf5c9ab2a`). 2.1.0
keeps 2.0.3's OAuth state, so after a rollback by either path above:

- Every live token keeps working, and no client needs a new sign-in or
  consent. Revoked installations stay revoked.
- Installation labels, hints and `last_used` are kept: 2.0.3 knows every field
  2.1.0 writes.
- The hook ranks and selects as in 2.0.3 again. Sessions the server
  remembered are forgotten at the restart either way.

Upgrading to 2.1.0 again needs no migration and no consent.

## Known issues

- [#232](https://github.com/acoz-labs/mandalore/issues/232): the hook still
  injects on some prompts that should get nothing, through the coverage,
  evidence and summary paths and through name collisions; a two-word prompt
  that shares one generic body word can inject; and a filler-heavy wrapper
  around a short question can still leave it without context.
- [#228](https://github.com/acoz-labs/mandalore/issues/228): the Claude
  plugin doesn't send a session yet, so Claude Code sessions get no
  de-duplication.
- [#229](https://github.com/acoz-labs/mandalore/issues/229): installed
  plugins track `main`, so a plugin change reaches installations before the
  matching server release.
- [#225](https://github.com/acoz-labs/mandalore/issues/225): a Claude Code
  installation's device label can exceed the 256-byte limit when its metadata
  document's host is very long, and its writes are then refused.
- [#223](https://github.com/acoz-labs/mandalore/issues/223): the label and
  hint sanitizers let Unicode line and paragraph separators through.
- [#221](https://github.com/acoz-labs/mandalore/issues/221): when an
  authorization code is replayed and revoking the first redemption's tokens
  fails on a store error, `/token` still answers `invalid_grant` and those
  tokens stay live.
- [#218](https://github.com/acoz-labs/mandalore/issues/218): a migrated Claude
  Code installation still shows its client's grant on every signet.
- [#216](https://github.com/acoz-labs/mandalore/issues/216): no test covers the
  publisher's refusal of a release-list page with more entries than it asked
  for.
- [#188](https://github.com/acoz-labs/mandalore/issues/188): no container image
  is published yet.
