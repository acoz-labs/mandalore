# Mandalore 2.0.2

[Release 2.0.2](https://github.com/acoz-labs/mandalore/releases/tag/v2.0.2)
keeps OAuth grants per installation, so a new Claude Code installation needs
the owner's consent instead of inheriting another installation's access, and
the owner can revoke or narrow one installation at a time. It also fixes OAuth
answers when the server state can't be read, explains a claude.ai connector
that hides the plugin's server, makes the Actions-only release commands
refuse locally, and lets the publisher read a release history larger than
128 KiB.

2.0.2 migrates the OAuth state file in place. Every live token keeps working,
and no client needs a new sign-in or consent because of the upgrade. See
[Upgrading OAuth state](#upgrading-oauth-state). It adds no public HTTP or OAuth
path, so the [Cloudflare WAF](../deploy/cloudflare-tunnel.md) allow list needs
no change. It changes no signet format or configuration.

container image: build from packaging/server; published image to follow.
([#188](https://github.com/acoz-labs/mandalore/issues/188); see
[Docker](../server.md#docker).)

## What changed

- **Grants per installation**
  ([#202](https://github.com/acoz-labs/mandalore/issues/202)). Every Claude Code
  installation signs in with the same client ID metadata document, so 2.0.1
  stored one grant for all of them: a second machine's sign-in got no consent
  page and inherited the first one's scope, and the owner could revoke only all
  of them at once. Now:
  - Each approval of a metadata-document client creates an installation, with
    its own grant and its own token family. Every authorization of such a
    client shows the consent page, after the owner's passkey sign-in; when other
    installations are approved, the page says this one is new and doesn't share
    their access. The server can't tell a returning installation from a new
    one, since they share a `client_id`, so a fresh sign-in (after a logout, a
    revoke or 30 days unused) also asks for consent.
  - A DCR registration, such as a hosted app's, belongs to one installation. It
    keeps skipping the consent page when it authorizes again, as before.
  - `server clients list` shows one entry per installation, with its ID
    (`inst-…`), first-seen and last-used times, grants and live tokens.
  - `server clients revoke --installation ID` and `server clients set-scope
    --installation ID` act on one installation; the others keep working.
    `--client ID` still acts on every installation of the client, and the
    answer says so and counts them.
  - A replayed refresh token, a logout through `/revoke` or a revoke ends that
    installation's family only.

  See [Installations](../server.md#oauth) and
  [Admin commands](../server.md#admin-commands).
- **OAuth answers when the state can't be read**
  ([#203](https://github.com/acoz-labs/mandalore/issues/203)). If
  `state_dir/oauth.json` is unreadable or corrupt, `POST /revoke` answers `503
  temporarily_unavailable` and revokes nothing, and `POST /token` answers `500
  server_error`. Both used to say "unknown client", which told a client its
  registration was gone. Unknown-client, cross-client and unknown-token answers
  are unchanged.
- **A claude.ai connector that replaces the plugin's server**
  ([#201](https://github.com/acoz-labs/mandalore/issues/201)). When a claude.ai
  custom connector has the plugin's server URL, Claude Code keeps the connector
  and drops `plugin:mandalore:mandalore`, so recall injects nothing. The plugin
  README explains it and gives the `deniedMcpServers` fix, and the Armorer
  diagnoses it and prints the entry to add. See
  [Plugin and connector together](../../plugins/claude/README.md#plugin-and-connector-together).
- **Actions-only release commands refuse locally**
  ([#205](https://github.com/acoz-labs/mandalore/issues/205)).
  `bin/finalize-release artifact` (with or without `--preflight`) and
  `bin/promote-candidate` exit 64 outside GitHub Actions and name the local
  release steps instead. This affects maintainers only; see
  [Publication](../delivery.md#publication-and-recovery).
- **The publisher reads a larger release history**
  ([#214](https://github.com/acoz-labs/mandalore/issues/214)). Before
  publishing, the publisher lists every release, drafts included, to find one
  with the same tag. It read pages of 100 releases under the 128 KiB limit for
  one metadata response. Full metadata runs about 15 KiB a release, so with ten
  releases the first page no longer fit, and publishing refused with "release
  response exceeds its size limit" before writing anything. It now reads pages
  of 20 releases, at most 1 MiB each and 4 MiB in all (ten pages, 200
  releases), and refuses past either bound. This affects maintainers only.

## Upgrading OAuth state

2.0.2 reads a 2.0.1 `oauth.json` and migrates it the first time it reads it,
in the server and in the admin CLI alike:

- **A DCR client** (a hosted app such as claude.ai) becomes one installation
  with its grants and all its tokens. Its tokens keep working, and its next
  authorization skips the consent page as before.
- **A metadata-document client** (Claude Code) becomes one installation per
  live token family, each with the client's 2.0.1 grant, because 2.0.1 didn't
  record which installation was approved with which scope. Several machines
  sharing the client become several installations, each still signed in. After
  the upgrade, check `server clients list` and narrow or revoke any that
  shouldn't have the shared scope.
- A metadata-document client whose tokens had all expired has no installation
  to keep. Its next sign-in shows the consent page, as any new installation's
  does.
- Migrated installations show the client's registration time as first seen.

No kind of client needs a new sign-in or consent because of the upgrade. The
migration is covered by `TestMigrationKeepsVersion1Grants`, on a synthetic
2.0.1 state with one metadata-document client used by three installations, a
hosted-app DCR client, a pending registration and an expired client.

## Upgrading a running launchd server

Installing 2.0.2 changes nothing for the process that is already running;
restart it afterwards. First check which executable the agent runs:

```sh
plutil -extract ProgramArguments.0 raw ~/Library/LaunchAgents/dev.acoz.mandalore.server.plist
```

If it shows the launcher, `PREFIX/bin/mandalore`, with `PREFIX/lib/mandalore`
present, follow [A launcher-managed install](#a-launcher-managed-install). If
`PREFIX/bin/mandalore` is a regular file and there is no `PREFIX/lib/mandalore`,
follow [A bare-binary install](#a-bare-binary-install). If it shows a runtime
under `PREFIX/lib/mandalore/releases/`, a CLI install never changes what the
agent runs: after installing, run `server uninstall-launchd`, then `server
install-launchd` again from the launcher.

### A launcher-managed install

1. Install 2.0.2 into the same prefix while the server runs:

   ```sh
   curl -fsSLO https://github.com/acoz-labs/mandalore/releases/download/v2.0.2/install.sh
   sh install.sh 2.0.2
   ```

   or `mandalore release install --version 2.0.2 --prefix PREFIX`. This switches the
   launcher to the 2.0.2 runtime and keeps 2.0.1 retained. The running server
   keeps serving 2.0.1 with the same PID.
2. Restart the agent. Plain `kickstart` does nothing to a running job; `-k`
   stops it first:

   ```sh
   launchctl kickstart -k gui/$(id -u)/dev.acoz.mandalore.server
   ```

3. Confirm 2.0.2 is serving:

   ```sh
   launchctl print gui/$(id -u)/dev.acoz.mandalore.server | grep -E '^\t(state|pid|runs) ='
   lsof -p PID -Fn | grep -m1 '/mandalore$'      # PID from the line above
   mandalore version                              # "version":"2.0.2"
   mandalore server clients list --config FILE
   ```

   `launchctl print` shows `state = running` with a new PID, and `lsof` names a
   runtime under `releases/sha256-MANIFEST/` other than 2.0.1's `511210ea…`.
   `server clients list` shows an `installation` ID on every approved entry.
   Then run `mandalore server status --config FILE`.

To roll back to 2.0.1:

```sh
mandalore release install --retained 511210eaf6605baa2a2f39e06b74a27cb5a9a9b407063614785c598a7d08c5d0 --prefix PREFIX
launchctl kickstart -k gui/$(id -u)/dev.acoz.mandalore.server
```

The mapped runtime is then under `releases/sha256-511210ea…/`. Return to 2.0.2
with `sh install.sh 2.0.2`, or its retained runtime under `release install
--retained`, and restart again.

### A bare-binary install

Where the agent runs a release binary copied to `PREFIX/bin/mandalore` by
hand, neither `release install` nor `install.sh` can upgrade it: both refuse
that prefix and change nothing. Swap the binary instead:

1. Download `mandalore_2.0.2_OS_ARCH` and `SHA256SUMS` from the release and
   check the binary with `shasum -a 256 -c --ignore-missing SHA256SUMS`.
2. Keep the old binary and swap in the new one atomically, in the same
   directory, then restart:

   ```sh
   cp -p PREFIX/bin/mandalore PREFIX/bin/mandalore-2.0.1
   cp mandalore_2.0.2_OS_ARCH PREFIX/bin/.mandalore.new && chmod 755 PREFIX/bin/.mandalore.new
   mv -f PREFIX/bin/.mandalore.new PREFIX/bin/mandalore
   launchctl kickstart -k gui/$(id -u)/LABEL
   ```

   The running server keeps serving 2.0.1 until the restart.
3. Confirm as above: a new PID, `PREFIX/bin/mandalore version` reports 2.0.2,
   `server clients list` shows installation IDs, and `server status` is ok.

To roll back, keep the 2.0.2 binary too, then move the old one back:

```sh
cp -p PREFIX/bin/mandalore PREFIX/bin/mandalore-2.0.2
mv -f PREFIX/bin/mandalore-2.0.1 PREFIX/bin/mandalore
launchctl kickstart -k gui/$(id -u)/LABEL
```

A Docker server is rebuilt from the new tag (`git clone --branch v2.0.2`, see
[Docker](../server.md#docker)) and restarted with the same volumes.

## Recovery

Previous artifact: [2.0.1](2.0.1.md) (manifest
`511210eaf6605baa2a2f39e06b74a27cb5a9a9b407063614785c598a7d08c5d0`). Every
2.0.2 save also writes each client's widest installation grant in the field
2.0.1 reads, so after a rollback, by either path above:

- Every live token keeps working, and no client needs a new sign-in.
- Tokens of revoked installations stay revoked.
- Grants are per client again, as in 2.0.1. A Claude Code sign-in skips consent
  once any installation of it is approved, and an installation narrowed with
  `set-scope --installation` gets its client's widest grant back, up to the
  scope its tokens were issued with. Narrow it again with `set-scope --client`
  if needed.

Upgrading to 2.0.2 again migrates the state 2.0.1 wrote, as above. That
resets every `set-scope` narrowing made before the rollback: each installation
gets its client's widest 2.0.1 grant again. After re-upgrading, check
`server clients list` and apply those narrowings again with `set-scope
--installation`.
