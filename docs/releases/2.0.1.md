# Mandalore 2.0.1

[Release 2.0.1](https://github.com/acoz-labs/mandalore/releases/tag/v2.0.1)
fixes the issues found while accepting and publishing
[2.0.0](2.0.0.md) and adds an OAuth revocation endpoint, so a client's logout
ends its tokens on the server. It changes no signet format, configuration or
server state: 2.0.1 reads a 2.0.0 server's state as it is, and 2.0.0 reads it
back after a rollback. One rollout step applies to servers behind the
documented Cloudflare tunnel: [allow `/revoke`](#rollout).

[#197](https://github.com/acoz-labs/mandalore/pull/197),
[#198](https://github.com/acoz-labs/mandalore/pull/198),

The independently accepted retained files were published without rebuilding:

## What changed

- **OAuth errors tell clients to authorize again**
  ([#191](https://github.com/acoz-labs/mandalore/issues/191)). A request that
  presents an unknown, expired or revoked bearer token, or one issued for
  another signet, gets `401` with
  `WWW-Authenticate: Bearer error="invalid_token", resource_metadata="..."`
  (RFC 6750 §3.1). A request with no token still gets the bare challenge,
  `Bearer resource_metadata="..."`. A refresh from an unknown or revoked client
  gets `400 invalid_grant` instead of `401 invalid_client`, so the client runs
  authorization again, which still needs the owner's passkey and consent. See
  [Authentication](../server.md#authentication).
- **Token revocation** ([#192](https://github.com/acoz-labs/mandalore/issues/192)).
  A new public endpoint, `POST /revoke` (RFC 7009), is advertised as
  `revocation_endpoint` in the authorization-server metadata. A client names
  itself with `client_id`, as at `/token`, and can revoke only its own tokens.
  Revoking either token of a pair ends the authorization's whole token family.
  An unknown token or another client's token gets the same empty `200` and
  changes nothing; the client's own expired token, if not yet pruned, still ends
  its family. `claude mcp logout` calls it, so a logout now leaves the
  client with no live tokens. See [OAuth](../server.md#oauth).
- **Preflight on clones with a large canon cache**
  ([#196](https://github.com/acoz-labs/mandalore/issues/196)).
  `server migrate preflight` (and the dirty check) no longer lists ignored files
  under `.mandalore/`, so a large ignored canon cache no longer pushes the
  listing past the 1 MiB Git output limit. Decisions for every other path are
  unchanged. An output-limit failure now names the command and the limit
  instead of reporting "not a standalone Git checkout".
- **Release tools check the published assets against the manifest**
  ([#193](https://github.com/acoz-labs/mandalore/issues/193)).
  `bin/promote-local-candidate`, `bin/promote-candidate`,
  `bin/release-publication verify` and `bin/finalize-release` required the eight
  1.x assets, so they exited 1 after every good 2.0 publish. They now require
  exactly the inventory the accepted manifest implies (its payloads,
  `manifest.json` and `SHA256SUMS`, each once with the manifest's digest).
- **Install preview shows real compatibility**
  ([#194](https://github.com/acoz-labs/mandalore/issues/194)). The preview's
  "Protocol / signet schema" was a constant `1 / read 1, write 1`. It now shows
  the selected manifest's values (`1 / read 1, 2; write 1, 2` for 2.0) and, in
  "Previous protocol / signet schema", those of the runtime installed in the
  prefix, read from its retained manifest. The 2.0.0 launcher still shows the
  constant when it previews 2.0.1; the fixed preview starts with 2.0.1.

## Rollout

**Behind the documented Cloudflare tunnel, allow `/revoke` before or with the
upgrade.** [WAF rule 1](../deploy/cloudflare-tunnel.md) blocks every path that
is not on its allow list, and the 2.0.0 list has no `/revoke`. Add it to the
path set, with no IP rule or challenge, since OAuth protects it:

```
http.request.uri.path in {"/authorize" "/consent" "/token" "/revoke" "/register" "/mcp"}
```

Without it, `/revoke` gets Cloudflare's `403`, and a client logout clears only
its local credentials: its tokens stay live on the server until they expire or
the owner runs `server clients revoke`. If you also keep an IP allowlist on
`/mcp` and `/token`, add `/revoke` to that rule too.

## Upgrading a running launchd server

An in-place upgrade over a running 2.0.0 launchd server works, but it needs a
restart: installing 2.0.1 changes nothing for the process that is already
running.

1. Check which executable the agent runs:

   ```sh
   plutil -extract ProgramArguments.0 raw ~/Library/LaunchAgents/dev.acoz.mandalore.server.plist
   ```

   `server install-launchd` records the path you ran it from. If it shows the
   launcher, `PREFIX/bin/mandalore`, the steps below apply. If it shows a
   runtime under `PREFIX/lib/mandalore/releases/`, a CLI install never changes
   what the agent runs: after installing, run `server uninstall-launchd`, then
   `server install-launchd` again from the launcher. If `PREFIX/bin/mandalore`
   is a regular file and there is no `PREFIX/lib/mandalore`, it is a bare
   release binary: see [A bare-binary install](#a-bare-binary-install).
2. Install 2.0.1 into the same prefix while the server runs, with the 2.0
   bootstrap or `mandalore release install`:

   ```sh
   curl -fsSLO https://github.com/acoz-labs/mandalore/releases/download/v2.0.1/install.sh
   sh install.sh 2.0.1
   ```

   This switches the launcher to the 2.0.1 runtime and keeps 2.0.0 retained. The
   running server keeps serving 2.0.0 with the same PID.
3. Restart the agent. Plain `kickstart` does nothing to a running job; `-k`
   stops it first:

   ```sh
   launchctl kickstart -k gui/$(id -u)/dev.acoz.mandalore.server
   ```

4. Confirm 2.0.1 is serving. The MCP server reports only its major version, so
   check the process and a 2.0.1 endpoint:

   ```sh
   launchctl print gui/$(id -u)/dev.acoz.mandalore.server | grep -E '^\t(state|pid|runs) ='
   lsof -p PID -Fn | grep -m1 '/mandalore$'      # PID from the line above
   mandalore version                              # "version":"2.0.1"
   curl -s -o /dev/null -w '%{http_code}\n' -X POST -H 'Host: localhost:8730' http://127.0.0.1:8730/revoke
   ```

   `launchctl print` shows `state = running` with a new PID. `lsof` names the
   runtime under `releases/sha256-511210ea…/` (2.0.1's manifest), not
   `releases/sha256-f9ffce7c…/` (2.0.0's). `/revoke`
   answers `400` (no `client_id`) on 2.0.1 and `404` on 2.0.0. Use the host and
   port from your `public_url` and `listen`; with `loopback-trust` there are no
   OAuth endpoints, so rely on `lsof`. Then run `mandalore server status --config
   FILE`.

### A bare-binary install

Where the agent runs a release binary copied to `PREFIX/bin/mandalore` by
hand, with no `PREFIX/lib/mandalore`, neither `release install` nor `install.sh`
can upgrade it. Both stop at planning with "launcher exists without a verified
Mandalore ownership receipt; refusing takeover" and change nothing. Replace the
binary instead, then restart:

1. Download `mandalore_2.0.1_OS_ARCH` and `SHA256SUMS` from the release and
   check the binary with `shasum -a 256 -c --ignore-missing SHA256SUMS`.
2. Keep the old binary and swap in the new one atomically, in the same
   directory:

   ```sh
   cp -p PREFIX/bin/mandalore PREFIX/bin/mandalore-2.0.0
   cp mandalore_2.0.1_OS_ARCH PREFIX/bin/.mandalore.new && chmod 755 PREFIX/bin/.mandalore.new
   mv -f PREFIX/bin/.mandalore.new PREFIX/bin/mandalore
   launchctl kickstart -k gui/$(id -u)/LABEL
   ```

   The running server keeps serving 2.0.0 until the restart.
3. Confirm as in step 4 above: a new PID, `PREFIX/bin/mandalore version`
   reports 2.0.1, `POST /revoke` answers `400`, and `server status` is ok.
   Existing clients and their tokens keep working.

To roll back, first keep the 2.0.1 binary too, since the `mv` consumes
`mandalore-2.0.0`, so rolling forward again needs no download:

```sh
cp -p PREFIX/bin/mandalore PREFIX/bin/mandalore-2.0.1
mv -f PREFIX/bin/mandalore-2.0.0 PREFIX/bin/mandalore
launchctl kickstart -k gui/$(id -u)/LABEL
```

`/revoke` then answers `404`. 2.0.0 reads the state 2.0.1 wrote: tokens it
refreshed keep working, tokens revoked through `/revoke` stay revoked, and its
canon cache is served.

To move to the managed launcher, which keeps retained runtimes for
`release install --retained`, move the bare binary aside
(`mv PREFIX/bin/mandalore PREFIX/bin/mandalore-bare`), install 2.0.0 and then
2.0.1 with `release install` (or `sh install.sh`), and `kickstart -k`. The
launcher takes the same `PREFIX/bin/mandalore` path, so the plist doesn't
change. Install 2.0.0 first: a launcher prefix that never held 2.0.0 has no
retained 2.0.0 to roll back to.

A Docker server is rebuilt from the new tag (`git clone --branch v2.0.1`, see
[Docker](../server.md#docker)) and restarted with the same volumes.

## Recovery

Previous artifact: [2.0.0](2.0.0.md) (manifest
`f9ffce7c637baa4623a1106163fceba1427a6102862204a327de8b8805107d44`). 2.0.1
adds no state format or field, so rolling back is a CLI switch and a restart:

```sh
mandalore release install --retained f9ffce7c637baa4623a1106163fceba1427a6102862204a327de8b8805107d44 --prefix PREFIX
launchctl kickstart -k gui/$(id -u)/dev.acoz.mandalore.server
```

Confirm it as in step 4: the mapped runtime is under
`releases/sha256-f9ffce7c…/` and `/revoke` answers `404`. Clients, grants and
tokens stay as they were. Tokens revoked through `/revoke` stay revoked. Return
to 2.0.1 with `sh install.sh 2.0.1`, or its retained runtime under
`release install --retained`, and restart again.

## Evidence and scope

[Acceptance](https://github.com/acoz-labs/mandalore/issues/194#issuecomment-6400108667)
([receipt](https://github.com/acoz-labs/mandalore/issues/194#issuecomment-6400142542))
was run by the independent maintainer against the retained candidate
`mandalore:d7c1b0f3efc9a278c36acd7dcdf418564ef8ea57:sha256:511210eaf6605baa2a2f39e06b74a27cb5a9a9b407063614785c598a7d08c5d0`,
on synthetic signets in temporary directories only:

- **Retained distribution:** `bin/build-artifacts` from a clean worktree at
  `d7c1b0f` gave the seven files, and `bin/promote-local-candidate
  --verify-only` passed for that identity. A rebuild from `v2.0.0` reproduces
  the published 2.0.0 manifest.
- **The #194 fix:** a fresh install previews `1 / read 1, 2; write 1, 2` with
  no previous runtime, and the 2.0.1 launcher shows both values when rolling
  back. The 2.0.0 launcher still prints its constant.
- **In place over a running launchd 2.0.0 server**, installed from the
  launcher: after `release install` the server kept its PID and served 2.0.0,
  also after a plain `kickstart`. After `kickstart -k` it served 2.0.1: `/revoke`
  `400`, `invalid_token` for a presented bogus bearer, the bare challenge with
  no bearer, and `invalid_grant` for a refresh from an unknown client. Rollback
  with `--retained f9ffce7c…` and forward again with `--retained 511210ea…`
  each took effect after `kickstart -k`, and a client registered under 2.0.0
  stayed known throughout.
- **Refusals:** a candidate binary with an appended byte, an edited manifest
  version, a foreign launcher, and an installed runtime tampered at the same
  size.

[Publication](https://github.com/acoz-labs/mandalore/issues/194#issuecomment-6400192361)
([receipt](https://github.com/acoz-labs/mandalore/issues/194#issuecomment-6400198690))
was by the independent maintainer through `bin/promote-local-candidate` after
the release gate passed. It exited 0 with `publication-verified` and seven
assets, the first clean exit since #193.

- **Same bytes:** `bin/release-publication verify` passes for this identity.
  All seven assets, downloaded fresh, are byte-identical to the accepted
  candidate and pass `SHA256SUMS`, and `manifest.json` hashes to `511210ea…`.
  `gh release verify v2.0.1` passes, with the tag resolving to `d7c1b0f`.
- **Immutable:** v2.0.1 is immutable and marked Latest. v2.0.0's release,
  assets and tag are unchanged.
- **Public installation:** the published `sh install.sh 2.0.1` over a 2.0.0
  install in a temporary home verified the checksum, showed both compatibility
  lines and installed 2.0.1 with 2.0.0 retained. Rollback with `--retained
  f9ffce7c…` and forward again with `--retained 511210ea…` both passed.

The [bare-binary and 1.6.1 checks](https://github.com/acoz-labs/mandalore/issues/194#issuecomment-6400238114)
were run by the implementer on synthetic installs with the 2.0.1 bytes:

- **[A bare-binary install](#a-bare-binary-install):** the swap and `kickstart
  -k`, then the rollback, with real OAuth state (an owner passkey, an approved
  client, refreshed and revoked token families), a populated canon cache and
  MCP writes. Each version read what the other wrote. `release install`
  refused the bare-binary prefix and left it unchanged.
- **From 1.6.1:** the published `sh install.sh 2.0.1` updated a 1.6.1 install
  in place with 1.6.1 retained, and `--retained` rolled it back.

The bare-binary swap was also run on a production bare-binary install. After
`kickstart -k`, 2.0.1 served, `/revoke` answered `400` locally and through the
tunnel, and existing sign-ins kept working.

The [earlier upgrade run](https://github.com/acoz-labs/mandalore/pull/204#issuecomment-6399939833)
on #204's head covers the same launcher steps.

Out of scope: darwin/amd64, linux/amd64 and linux/arm64 had no native host here
(cross-builds aren't native acceptance), live OAuth tokens across a
launcher-managed upgrade, and the live Cloudflare WAF rule. A release is not
proof that any machine updated.

## Known issues

- [#201](https://github.com/acoz-labs/mandalore/issues/201): when a claude.ai
  connector points at the same server, Claude Code keeps the synced connector
  and drops the plugin's server, so the plugin's recall hook silently injects
  nothing. The issue gives a settings workaround.
- [#202](https://github.com/acoz-labs/mandalore/issues/202): every Claude Code
  installation shares one client ID metadata document, and grants are kept per
  `client_id`, so a new installation inherits an approved installation's
  consent, and `server clients revoke` can't revoke one installation alone.
- [#203](https://github.com/acoz-labs/mandalore/issues/203): when the OAuth
  state can't be read, `/revoke` and `/token` answer as if the client were
  unknown instead of `503`/`500`.
- [#205](https://github.com/acoz-labs/mandalore/issues/205): `bin/finalize-release
  artifact` can't pass outside the disabled Actions release path.
- [#188](https://github.com/acoz-labs/mandalore/issues/188): no container image
  is published yet.
