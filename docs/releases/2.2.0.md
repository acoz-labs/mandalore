# Mandalore 2.2.0

[Release 2.2.0](https://github.com/acoz-labs/mandalore/releases/tag/v2.2.0)
adds topics, which users may call bounties: a project, account or task scope
with a name and description that any agent on any client can find by name and
load in one call. The server and the Claude plugin ship together at 2.2.0.

**Upgrade every clone that syncs before anyone names a topic.** Names and
scoped journal entries are new files under `memory/scopes/`, with no signet
format change. A 2.1.2 server keeps serving such a signet, without the names,
but its reconcile, checkpoint and export refuse the new files until it runs
2.2.0. Nothing is lost when they refuse. The full list is in
[the signet format](../signet-format.md#scope-labels-and-scoped-journals).

2.2.0 changes no OAuth state version, no signet manifest version, no state
file and no configuration, and adds no public HTTP or OAuth path, so the
Cloudflare path allowlist needs no change.

## What changed

- **Topics** ([#246](https://github.com/acoz-labs/mandalore/issues/246)).
  They are named scopes, not a new scope kind; the
  [server guide](../server.md#topics-bounties) has the details.
  - `memory_name_scope` (read-write) names a scope or revises its name and
    description, with `request_id` idempotency like `memory_remember`.
    Concurrent renames stay visible as several current names.
  - `memory_scopes` returns each scope's current names and takes a `query`
    matched against ID, name and description. Scopes with only a name or
    scoped journal entries are listed with `record_count` 0.
  - `memory_prime` (read) loads a topic in one call: its names, its
    `project-state` records in full, conflicts, other current records as
    summaries without bodies, and its journal, each newest first, within a
    byte budget that drops whole items and says so.
  - `memory_journal_append` takes an optional `entry.scope`, and
    `memory_journal` an optional `scope` filter. Unscoped entries are
    unchanged and still returned by an unfiltered query.
  - The CLI reaches the same operations (`memory scopes --query`,
    `memory journal --scope-kind/--scope-id`, `memory prime`,
    `memory name-scope`).
- **Export reports** select a scope's labels and scoped journal entries with
  its records, as `scope_label` items in the existing field categories.
- **Canon** fetches, verifies and serves a source signet that has topic files.
- **Guidance.** The server instructions gain one sentence on the topic
  workflow, and the plugin's `this-is-the-way` skill a short Topics paragraph
  that applies only when the server lists `memory_prime`.

`memory_context`, the recall hook, is unchanged: it neither reads names nor
selects or packs differently.

## Upgrading

Upgrade the server as [2.1.0's notes](2.1.0.md#upgrading-a-running-launchd-server)
describe, using 2.2.0 in place of 2.1.0, and do the same for every other
server or clone that syncs the same signet. No signet or state changes.

The plugin reaches installations when this release's PR merges, before the
server is upgraded ([#229](https://github.com/acoz-labs/mandalore/issues/229)).
That is safe on 2.1.2: the skill's topic steps apply only when the server
lists `memory_prime`, and a stray `entry.scope` is refused by 2.1.2 as
`input.invalid` with nothing written.

## Recovery

Previous artifact: [2.1.2](2.1.2.md). Rolling back changes no existing data:
2.1.2 reads every record and unscoped journal entry as before. If names or
scoped journal entries were written, 2.1.2 can't reconcile, checkpoint or
export that signet until 2.2.0 is back. They can't be removed without editing
append-only history. Their intent files in `.mandalore/` also make 2.1.2's
cutover preflight report "pending write intents are unreadable", and a
journal retry that reuses such a `request_id` returns `save.incomplete`
without writing. Roll back before the first name to avoid all of this.

The independent maintainer reviewed #247 and
[requested changes](https://github.com/acoz-labs/mandalore/pull/247#pullrequestreview-5848987755)
in round 1, with one high finding: two clones that named the same scope
before syncing left the second unable ever to sync. After the fix (a scope
may have several first names, shown as a conflict) and four lows, the
maintainer
[approved](https://github.com/acoz-labs/mandalore/pull/247#pullrequestreview-5849137886)
it in round 2 at exactly `687cecc`
([pre-merge receipt](https://github.com/acoz-labs/mandalore/pull/247#issuecomment-6778915021)),
then [nominated](https://github.com/acoz-labs/mandalore/issues/246#issuecomment-6779045886)
and [accepted](https://github.com/acoz-labs/mandalore/issues/246#issuecomment-6779154791)
([receipt](https://github.com/acoz-labs/mandalore/issues/246#issuecomment-6779239130))
the retained candidate
`mandalore:0d3c22daf8d9cb07a229126a508155d5b4e40d9e:sha256:6cda938922f7027e60a15189c67cda4b556bfb4fa9d926a0ad044cbe5c2fc579`.
`bin/sdlc audit --before 79b378e --sha 0d3c22d` passed. Acceptance used
synthetic state only, with a temporary `HOME`; the old side was the
published, checksum-verified 2.1.2.

- **Retained distribution:** `bin/build-artifacts` at `0d3c22d`, in a clean
  worktree, gave the seven files for 2.2.0, and `SHA256SUMS` verifies them.
  `install.sh` is byte-identical to 2.1.2's, and the darwin/arm64 binary
  (`d472290f…`) passes `codesign -v`. `bin/promote-local-candidate
  --verify-only` passed for that identity and refused a copy with one byte
  appended.
- **Issue criteria (#246):** the retained darwin/arm64 binary served a fresh
  synthetic signet over HTTP MCP, with installation A read-write and
  installation B read-only, each with its own config and state. The main pass
  ran on format 2 and a second pass on format 1 without the withdrawal.
  - A named a topic, saved three records in its scope including a
    `project-state`, and appended two scoped journal entries.
  - B, given only the display name, found the topic with a `memory_scopes`
    query and primed on it. The prime led with the description, then the
    `project-state` record, then the other records as summaries, then the
    journal, newest first.
  - After A corrected the state and withdrew a record (format 2), B's next
    prime showed only the new state and not the withdrawn record.
  - At the minimum budget of 1024 bytes the prime was 1004 bytes and kept the
    name, the description and the state, with `truncated` true.
  - B isn't served `memory_name_scope` or `memory_journal_append`; both calls
    failed with `unknown tool`.
  - The format 1 and format 2 fixtures validate under the published 2.1.2
    and the candidate, with every file's bytes unchanged.
- **Compatibility with the published 2.1.2:** the old-reader test ran with
  the candidate and the published 2.1.2 and passed on both formats. On
  signets the candidate wrote topic files into, 2.1.2 served memory without
  names and didn't list the new tools. It refused `entry.scope` as
  `input.invalid` and a reused scoped `request_id` as `save.incomplete`,
  writing nothing. Its checkpoint, export preview, cutover preflight and
  reconcile refused, an ahead clone kept its unpushed commit, and canon
  refresh served the topic commit without names.
- **Native runtime and plugin:** the darwin/arm64 binary ran natively
  (`version`, `signet create`, `bind`, `checkpoint`, the signet upgrade,
  `serve`, MCP `tools/list` and `tools/call` for the topic tools, `release
  plan` and `apply`). Claude Code 2.1.322, fully isolated with a temporary
  `HOME` and `CLAUDE_CONFIG_DIR`, no token and no keychain link, installed
  plugin 2.2.0 from the merge's checkout. Its skill holds the conditional
  Topics paragraph, and its MCP server connected to the 2.2.0 server. The
  check reports installation and connection, not a model turn.
- **Upgrade, rollback and re-upgrade:** 2.1.2 → 2.2.0 → 2.1.2 → 2.2.0,
  - through the launcher, from the published 2.1.2 to the candidate, then
    `--retained 6cc86586…` and `--retained 6cda9389…`, each reporting the
    expected version;
  - as a bare binary, with the atomic swap, each step reporting the expected
    version.

  A fresh install into an empty prefix gave 2.2.0 at `0d3c22d`,
  byte-identical to the accepted binary, and a launcher without a Mandalore
  ownership receipt was refused and left untouched.

published. A release is not proof that any machine updated: the owner
upgrades the live server and every clone that syncs, before anyone names a
topic.
