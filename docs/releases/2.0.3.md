# Mandalore 2.0.3

[Release 2.0.3](https://github.com/acoz-labs/mandalore/releases/tag/v2.0.3)
records each Claude Code installation's writes as its own device, so two
machines that sign in with one `client_id` are told apart in history and
provenance. It also lets the owner tell installations apart in `server clients
list` (a label, a consent hint, a `last_used` that moves on MCP use) and marks
and prunes expired ones. And `/token` answers a server-side storage failure
with `server_error` and keeps the authorization code.

2.0.3 changes no OAuth state version, no signet format and no configuration.
Every live token keeps working, and no client needs a new sign-in or consent
because of the upgrade. It adds no public HTTP or OAuth path, so the
[Cloudflare WAF](../deploy/cloudflare-tunnel.md) allow list needs no change.

## What changed

- **Authorship per installation**
  ([#211](https://github.com/acoz-labs/mandalore/issues/211)). Every Claude
  Code installation signs in with the same client ID metadata document. In
  2.0.2 they all wrote as the client's one device, so one machine's writes
  couldn't be told from another's. Now:
  - Each installation of a metadata-document client enrolls its own device in
    the signet, labelled `<client name> installation <id> (<kind>), approved
    <date>`, on its approval or its first write. The `<id>` is the one
    `server clients list` shows.
  - A DCR client, such as a hosted app's, is one installation and keeps the
    device it already had.
  - Records written before 2.0.3 keep the authorship they were written with.
    Nothing is rewritten.
  - Writes through a claude.ai connector are recorded as the claude.ai client,
    including writes by Claude Code agents, which can call the account's
    connectors. To keep Claude Code's writes on its own installation, deny the
    connector in Claude Code with `deniedMcpServers`
    ([plugin and connector together](../../plugins/claude/README.md#plugin-and-connector-together)).

  See [Who wrote it](../server.md#who-wrote-it).
- **Telling installations apart**
  ([#217](https://github.com/acoz-labs/mandalore/issues/217)):
  - `server clients label --installation ID TEXT` sets the owner's label, plain
    text of at most 64 characters. An empty `TEXT` removes it.
  - The consent page records a hint: the first 120 characters of the
    approving browser's `User-Agent`, with no IP address.
  - `last_used` moves on authenticated MCP use, saved at most once a minute per
    installation, as well as on token issue and refresh.
  - `server clients list` shows the label, hint and status in its JSON output
    and in the new `--format text`.
- **Expired installations**
  ([#217](https://github.com/acoz-labs/mandalore/issues/217), folding in item
  1 of [#218](https://github.com/acoz-labs/mandalore/issues/218)). A Claude
  Code installation with no live token, including a family 2.0.2 migrated
  after all its tokens had expired, is listed as `expired`. The server prunes
  it a day after its last use, and `server clients prune` removes every
  expired installation at once.
- **`/token` storage failures**
  ([#209](https://github.com/acoz-labs/mandalore/issues/209)). If
  `state_dir/oauth.json` can't be read or saved during a code redemption or a
  refresh, `/token` answers `500 server_error` and issues nothing. It used to
  answer `400 invalid_grant`, which told the client its grant was bad. A
  redemption whose save failed keeps its authorization code, so the client can
  retry within the code's lifetime without a new sign-in. Real grant errors
  give the same answers as before.

## Labelling existing installations

After the upgrade, the installations that need a label are the Claude Code
installations that 2.0.2 migrated from 2.0.1. They have no hint, and all of
one client's show the same first seen. Installations approved under 2.0.2 have
no hint either. A DCR client, such as claude.ai, has one installation and is
already told apart by its name. An installation approved under 2.0.3 shows the
browser hint from its consent page.

Follow [Telling installations apart](../server.md#telling-installations-apart)
in docs/server.md. In short, for each machine:

1. Run `mandalore server clients list --config FILE --format text` and note
   each installation's `last used`.
2. On that machine, call any Mandalore tool, such as a recall, at least a
   minute after its previous call. Keep the other machines idle meanwhile.
3. List again. The installation whose `last used` moved is that machine. Label
   it:

   ```sh
   mandalore server clients label --config FILE --installation inst-0123456789abcdef "Work laptop"
   ```

Where an installation has a hint, it can be enough on its own to label it.
An `expired` installation has no live token, so no machine uses it:
`mandalore server clients prune --config FILE` removes it. An installation
whose `last used` never moves is one no machine is using any more; revoke it
with `server clients revoke --installation ID`.

The first write from each Claude Code installation after the upgrade enrolls
its device. Its provenance label carries the installation ID, so the label in
`server clients list` and the device in `memory_history` refer to the same
machine.

## Upgrading a running launchd server

Installing 2.0.3 changes nothing for the process that is already running;
restart it afterwards. First check which executable the agent runs:

```sh
plutil -extract ProgramArguments.0 raw ~/Library/LaunchAgents/dev.acoz.mandalore.server.plist
```

If it shows the launcher, `PREFIX/bin/mandalore`, with `PREFIX/lib/mandalore`
present, follow [A launcher-managed install](#a-launcher-managed-install). If
`PREFIX/bin/mandalore` is a regular file and there is no `PREFIX/lib/mandalore`,
follow [A bare-binary install](#a-bare-binary-install). If it shows a runtime
under `PREFIX/lib/mandalore/releases/`, a CLI install never changes what the
agent runs: after installing, run `server uninstall-launchd`, then `server
install-launchd` again from the launcher.

### A launcher-managed install

1. Install 2.0.3 into the same prefix while the server runs:

   ```sh
   curl -fsSLO https://github.com/acoz-labs/mandalore/releases/download/v2.0.3/install.sh
   sh install.sh 2.0.3
   ```

   or `mandalore release install --version 2.0.3 --prefix PREFIX`. This switches
   the launcher to the 2.0.3 runtime and keeps 2.0.2 retained. The running
   server keeps serving 2.0.2 with the same PID.
2. Restart the agent. Plain `kickstart` does nothing to a running job; `-k`
   stops it first:

   ```sh
   launchctl kickstart -k gui/$(id -u)/dev.acoz.mandalore.server
   ```

3. Confirm 2.0.3 is serving:

   ```sh
   launchctl print gui/$(id -u)/dev.acoz.mandalore.server | grep -E '^\t(state|pid|runs) ='
   lsof -p PID -Fn | grep -m1 '/mandalore$'      # PID from the line above
   mandalore version                              # "version":"2.0.3"
   mandalore server clients list --config FILE --format text
   ```

   `launchctl print` shows `state = running` with a new PID, and `lsof` names a
   runtime under `releases/sha256-84235230…/` (2.0.3's manifest), not
   `releases/sha256-8fb8aeb2…/` (2.0.2's). `--format text` is new in 2.0.3, so
   it also shows that the CLI is 2.0.3. Then run `mandalore server status
   --config FILE`.

To roll back to 2.0.2:

```sh
mandalore release install --retained 8fb8aeb295eb063accee9b0a356207b615348da5e82fc00bca818b40254bb270 --prefix PREFIX
launchctl kickstart -k gui/$(id -u)/dev.acoz.mandalore.server
```

The mapped runtime is then under `releases/sha256-8fb8aeb2…/`. Return to 2.0.3
with `sh install.sh 2.0.3`, or its retained runtime under `release install
--retained`, and restart again. Read [Recovery](#recovery) first: a rollback
loses labels and hints.

### A bare-binary install

Where the agent runs a release binary copied to `PREFIX/bin/mandalore` by
hand, neither `release install` nor `install.sh` can upgrade it: both refuse
that prefix and change nothing. Swap the binary instead:

1. Download `mandalore_2.0.3_OS_ARCH` and `SHA256SUMS` from the release and
   check the binary with `shasum -a 256 -c --ignore-missing SHA256SUMS`.
2. Keep the old binary and swap in the new one atomically, in the same
   directory, then restart:

   ```sh
   cp -p PREFIX/bin/mandalore PREFIX/bin/mandalore-2.0.2
   cp mandalore_2.0.3_OS_ARCH PREFIX/bin/.mandalore.new && chmod 755 PREFIX/bin/.mandalore.new
   mv -f PREFIX/bin/.mandalore.new PREFIX/bin/mandalore
   launchctl kickstart -k gui/$(id -u)/LABEL
   ```

   The running server keeps serving 2.0.2 until the restart.
3. Confirm as above: a new PID, `PREFIX/bin/mandalore version` reports 2.0.3,
   `server clients list --format text` works, and `server status` is ok.

To roll back, keep the 2.0.3 binary too, then move the old one back:

```sh
cp -p PREFIX/bin/mandalore PREFIX/bin/mandalore-2.0.3
mv -f PREFIX/bin/mandalore-2.0.2 PREFIX/bin/mandalore
launchctl kickstart -k gui/$(id -u)/LABEL
```

A Docker server is rebuilt from the new tag (`git clone --branch v2.0.3`, see
[Docker](../server.md#docker)) and restarted with the same volumes.

## Recovery

Previous artifact: [2.0.2](2.0.2.md) (manifest
`8fb8aeb295eb063accee9b0a356207b615348da5e82fc00bca818b40254bb270`). 2.0.3
keeps 2.0.2's state version, so after a rollback, by either path above:

- Every live token keeps working, and no client needs a new sign-in or
  consent. Revoked installations stay revoked.
- **Labels and hints are erased.** 2.0.2 doesn't know those fields and drops
  them the first time it saves the OAuth state: the next token issue or
  refresh, owner passkey sign-in, or admin command that changes the state,
  which in practice is within minutes. Copy `server clients list` before rolling
  back if you want to re-apply the labels afterwards.
- `last_used` moves only on token issue and refresh again. `server clients
  list` shows an expired installation as approved with 0 live tokens, and
  2.0.2 has no `prune` command; its server still removes the installation a
  day after its last use.
- Each Claude Code installation writes as its client's shared device again,
  as in 2.0.2. Records written under 2.0.3 keep their per-installation
  authorship. 2.0.2 keeps each installation's device in
  `state_dir/signets/SLUG/devices.json`, since it rewrites that file whole.

Upgrading to 2.0.3 again needs no migration and no consent:

- Each Claude Code installation writes as the device it enrolled under 2.0.3
  before the rollback. One approved during the rollback enrolls its own on its
  first write.
- Labels don't come back: label the installations again, as in [Labelling
  existing installations](#labelling-existing-installations).
- Hints come back only with a new consent, so installations approved before
  or during the rollback have none. Tell them apart by `last used`.
- Expired installations are marked `expired` again, and `server clients prune`
  works again.

## Known issues

- [#225](https://github.com/acoz-labs/mandalore/issues/225): a Claude Code
  installation's device label can exceed the 256-byte limit when its metadata
  document's host is very long, and its writes are then refused. Real hosts,
  such as `claude.ai`, are far below it.
- [#223](https://github.com/acoz-labs/mandalore/issues/223): the label and
  hint sanitizers let Unicode line and paragraph separators through, so a
  crafted User-Agent can break lines in `clients list --format text`, and a
  pending installation can be pruned a few milliseconds early.
- [#221](https://github.com/acoz-labs/mandalore/issues/221): when an
  authorization code is replayed and revoking the first redemption's tokens
  fails on a store error, `/token` still answers `invalid_grant` and those
  tokens stay live.
- [#218](https://github.com/acoz-labs/mandalore/issues/218): a migrated Claude
  Code installation still shows its client's grant on every signet.
- [#216](https://github.com/acoz-labs/mandalore/issues/216): no test covers the
  publisher's refusal of a release-list page with more entries than it asked
  for.
- [#188](https://github.com/acoz-labs/mandalore/issues/188): no container image
  is published yet.
