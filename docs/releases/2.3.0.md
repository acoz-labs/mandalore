# Mandalore 2.3.0

[Release 2.3.0](https://github.com/acoz-labs/mandalore/releases/tag/v2.3.0)
moves a misfiled record to another scope without losing its ID, content or
history. The server and the Claude plugin ship together at 2.3.0.

**Upgrade every clone that syncs before anyone moves a record.** A move is a
new file under `memory/moves/`, with no signet format change, and existing
data stays valid byte for byte. A 2.2.1 or 2.1.2 server keeps serving such a
signet, with the moved record in the scope it was saved in. But its
checkpoint, reconcile, menu sync, backup, upgrade and export refuse the new
file until it runs 2.3.0. Nothing is lost when they refuse. The full list is
in [the signet format](../signet-format.md#record-moves).

2.3.0 changes no OAuth state version, no signet manifest version, no state
file and no configuration, and adds no public HTTP or OAuth path, so the
Cloudflare path allowlist needs no change. It needs no new secret.

## What changed

- **Moving a record** ([#250](https://github.com/acoz-labs/mandalore/issues/250));
  the [server guide](../server.md#moving-a-record) has the details.
  - `memory_move` (read-write) moves a record to a project, account, task or
    signet-wide scope with a reason. It takes the record's current revision
    IDs and move heads, refuses stale ones as `memory.stale_heads`, and has
    `request_id` idempotency like `memory_remember`; a retry returns the
    first receipt, a no-op's too. A record already in the destination is
    left as is (`moved: false`). A withdrawn record must be restored first,
    and conflicting revisions settled first.
  - The move is new evidence with its authorship and reason. The stored
    revisions keep the scope the record was saved in; corrections after a
    move pass the new scope, and the old one is refused, naming the new.
  - Recall, prime, scopes, context, withheld-record discovery, export
    reports and canon find a moved record in its new scope only. On a signet
    with no moves their output is byte-identical to 2.2.1's.
  - Two clones that move a record to different scopes leave a move conflict:
    listed in each scope with `move_scopes`, counted as `move_conflicts`,
    and reported by synchronization as `conflicted`, until a move that names
    every move head settles it. Moves to the same scope agree.
  - The CLI reaches it as `memory move`.
- **`memory_history` output changes on every record**, moved or not: it gains
  `scope` (where the record is now), `move_heads`, `move_count` and, on the
  first page, `moves`. Each page holds the same revisions as before.
- **Export reports** select a record by its current scope and, with
  `include_history`, report its moves as `record_move` items.
- **Guidance.** The `memory_move` and `memory_remember` tool descriptions
  point at moving a misfiled record rather than copying and withdrawing it.
  The plugin's `this-is-the-way` skill gains the same line, and its
  reference gains a "Move a misfiled record" section and a note on which
  scope a correction takes; every line that names `memory_move` applies only
  when the server lists it. Three small changes aren't gated: the skill
  says a correction keeps the record's "current scope (`memory_history`
  shows it)", and the reference's title and the skill's link to it add
  "moves". They are inert on 2.2.1, where a record's current scope is the
  scope on its revisions, and titles give no instruction.

Recall ranking is unchanged; what changed is the scope each record is
selected in.

## Upgrading

Upgrade the server as [2.1.0's notes](2.1.0.md#upgrading-a-running-launchd-server)
describe, using 2.3.0 in place of 2.1.0, and do the same for every other
server or clone that syncs the same signet. No signet or state changes.

The plugin reaches installations when this release's PR merges, before the
server is upgraded ([#229](https://github.com/acoz-labs/mandalore/issues/229)).
That is safe on 2.2.1: every new plugin line that names `memory_move`
applies only when the server lists it, which 2.2.1 doesn't, and the three
ungated changes above are inert there. The plugin's hooks and `.mcp.json`
don't change.

## Recovery

Previous artifact: [2.2.1](2.2.1.md). Rolling back changes no existing data,
and moves can't be removed without editing append-only history. On 2.2.1 a
moved record shows in the scope it was saved in. A correction there saves,
and once 2.3.0 is back the record is still in its new scope, with that
content. But 2.2.1 can't checkpoint, reconcile, back up, upgrade or export
that signet until 2.3.0 is back: a server's writes save locally while its
backup stays pending, and `server status` shows the remote as unreachable.
`server migrate init` from such a remote stops after enrolling its device,
and `server migrate verify` stops after saving and withdrawing its canary.
Move intents in `.mandalore/` make 2.2.1's cutover preflight refuse, and a
`memory_remember` that reuses a move's `request_id` returns `save.incomplete`
without writing. Roll back before the first move to avoid all of this.

([pre-merge receipt](https://github.com/acoz-labs/mandalore/pull/251#issuecomment-6798867161)).

rounds first. The maintainer then
[nominated](https://github.com/acoz-labs/mandalore/issues/250#issuecomment-6799011073)
and [accepted](https://github.com/acoz-labs/mandalore/issues/250#issuecomment-6799084465)
([receipt](https://github.com/acoz-labs/mandalore/issues/250#issuecomment-6799178618))
the retained candidate built from `5438e36`. `bin/sdlc audit --before
21396eb --sha 5438e36` passed. Acceptance used synthetic state only, with a
temporary `HOME`; the old side was the published, checksum-verified 2.2.1
(manifest `a1a348ee…`).

- **Issue criteria (#250):** the retained darwin/arm64 binary served a
  synthetic format 2 signet over MCP, and each of the issue's six scenarios
  passed.
  - A record saved in one project, corrected and moved to another kept its
    `record_id`; recall and prime followed it to the new scope and not the
    old. History showed both revisions, the current scope and the move with
    its reason, authorship and `from`.
  - A correction in the old scope was refused, naming the new one, and one
    in the new scope succeeded.
  - Stale content and move heads got `memory.stale_heads`, a withdrawn
    record was refused with nothing written, a retry with the same
    `request_id` returned the first receipt, different input and cross-tool
    reuse got `request.conflict`, and a no-op returned `moved: false`.
  - Two clones, a server and the CLI's `memory move`, synced through the
    menu and `server reconcile` with three conflicted records: moves to
    different scopes, moves plus corrections, and moves plus withdrawals.
    Sync reported `conflicted` with 3 semantic conflicts and the move-aware
    notice, `memory_scopes` showed `move_conflicts: 3`, and the context hook
    named each move conflict. Corrections were refused during a move
    conflict, and a move naming every head settled it.
  - A read-only server didn't list `memory_move`, and the CLI's read-only
    call got `operation.read_only`.
  - `bin/ci` passed on the merge commit.

  `govulncheck` v1.9.0 at `5438e36` reports no reachable vulnerability, and
  binary mode is clean on all four binaries. `bin/check-old-reader` passed
  on the approved head against 2.1.2 and 2.2.1.
- **Recall eval:** the requester's private recall eval passed, as relayed
  by the lead; it isn't reproduced in the public evidence. It ran on a copy
  of the owner's signet, never the live one, and compared the candidate
  with the published 2.2.1: the output matched 2.2.1 line for line. The copy
  has no moves, so the eval didn't exercise `memory_move` itself; the
  synthetic scenarios above cover moves.
- **Retained distribution:** `bin/build-artifacts` at `5438e36`, in a clean
  worktree, gave the seven files for 2.3.0 with Go 1.26.11, and
  `SHA256SUMS` verifies them. `install.sh` is byte-identical to 2.2.1's,
  and the darwin/arm64 binary (`80ab974b…`) passes `codesign -v`.
  `bin/promote-local-candidate --verify-only` passed for that identity and

  `5438e36` and served over HTTP/1.1: `/healthz` answered 200, and
  `tools/list` listed 13 `memory_*` tools, including `memory_move`. Claude
  Code, fully isolated with a temporary `HOME` and `CLAUDE_CONFIG_DIR` and no

(cross-builds aren't native acceptance), native OAuth installations, a Claude
Code session driven by a model, and the live `launchctl kickstart -k` step of
the bare-binary upgrade. No container image is published. A release is not
proof that any machine updated: no live server was upgraded, and every server
and clone that syncs a signet should run 2.3.0 before anyone moves a record.
