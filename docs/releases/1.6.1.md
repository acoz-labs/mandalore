# Mandalore 1.6.1

[Release 1.6.1](https://github.com/acoz-labs/mandalore/releases/tag/v1.6.1)
fixes canon refresh timeouts for moderately sized references
([#156](https://github.com/acoz-labs/mandalore/issues/156)). Refresh used to
start one Git process per eligible blob, so a first refresh of a reference with
about 200 signet/provenance/memory blobs could use up the shared two-second
fetch budget and report `unavailable`/`timeout`. Refresh now reads the selected
objects in batches: one size check, then content batches capped by the Git
output bound. Each blob is rehashed against its tree identity, which is a new,
stricter check. A timeout receipt now names the phase that ran out in
`timeout_phase`: `fetch`, `materialize`, `validate` or `stale_validation`. It
never includes source content. The budget is unchanged: a three-second deadline,
a two-second shared fetch budget, the final second reserved for stale
validation, and no retries. See [foundlings](../foundlings.md).

Source: `1f07c67dd9b4bd705e84f74998eff5d9efbac70b` (implementation
[#158](https://github.com/acoz-labs/mandalore/pull/158)).

## Evidence and scope

[Acceptance observations](https://github.com/acoz-labs/mandalore/issues/156#issuecomment-6350674108)
used the actual release binaries with a synthetic 209-blob canon source served
over local HTTPS, with injected per-request latency. On macOS arm64, a first
refresh with no cache at 250 ms per request returned `unavailable/timeout` with
1.6.0 and `available` with 1.6.1. That held for both native session-start
refresh and explicit `foundling_refresh`. When the budget was exceeded, 1.6.1
returned `unavailable` with `timeout_phase=fetch` when there was no cache, and
`stale` from the verified snapshot when there was one. Linux arm64 behaved the
same for 1.6.1. Linux 1.6.0 did not reproduce the timeout at that latency,
because a Git process is cheap there.

The amd64 payloads received build and integrity verification only. The
`materialize`, `validate` and `stale_validation` phases are covered by source
tests, not by the release binaries. [Publication evidence](https://github.com/acoz-labs/mandalore/issues/156#issuecomment-6350811698)
covers same-byte downloads, immutable release metadata and public installation.

## Upgrade and recovery

Install or update through the usual release preview and apply flow. This release
has no signet schema or registration change and needs no data migration.
Recovery selects the retained 1.6.0 runtime
(`mandalore release plan --retained f3c0d3c283997c932fb07a5a198100d5eb75f8119cb18dc42971636ca59dfe65 --prefix PREFIX`,
then `release apply`) after stopping affected native sessions.

**Rollback caveat:** after rolling back to 1.6.0, any session receipt that
carries `timeout_phase` is rejected and reported as `no_session_snapshot`
until that session's next refresh rewrites it. Verified `verified-*` snapshots
never carry the field and remain usable for stale fallback.
