## Compatibility and limits

The minor version reflects additive interfaces and Pi support. Signet format,
shared protocol and manifest format remain version 1; no memory migration is
required or performed by candidate preparation. Existing local-only save tools
retain their names/defaults. Smaller initial foundling results are intentionally
expandable; they are not permission to stop a user-requested full review.

The clean-source builder stamps both native packages and the runtime from
VERSION in its private export. Source package manifests remain 0.0.0-dev. The
eight-file artifact inventory is unchanged: four platform executables, Codex
ZIP, installer, manifest and checksums. Pi is embedded in the runtime; its own
inspection reports its identity. Candidate identity combines source and manifest
digest; a version label alone is not proof of matching bytes or behavior.

Native engineering evidence currently covers macOS arm64, Codex 0.154.0 and Pi
0.85.1 with Node 24.1.0. Pi's declared Node minimum is 22.19.0; that declaration
is not proof of a native run on every allowed version. Cross-builds cover macOS
and Linux amd64/arm64 but are not native acceptance on those targets. Readiness
declarations separate intended support from immutable scenario evidence; a new
candidate can correctly have historical/unknown evidence, not a repair defect.

Unfinished work is explicit: lifecycle #55 O1/O2, export #80, withdrawal #81,
copyable narrow recovery commands #77, and Claude #14 after Pi acceptance.
The historical #19 trigger cause remains unproven but no longer blocks CI.
Normal learning and model-selected save-and-sync work without a special phrase;
neither is a deterministic compaction/exit safety net. Do not close these items
or claim the complete roadmap is delivered by preparing this candidate.

## Retain and nominate

After reviewed main passes required CI, use **Build retained candidate** once.
Record its exact source, run/attempt, artifact ID, archive digest and expiry.
Use **Nominate artifact candidate** with those exact coordinates; it independently
verifies provenance and all payloads through the existing guarded path. See
[retained candidate operations](../development.md#retained-actions-candidates).

Verify nomination receipts for #13, #56, #57, #61, #65, #74, #85 and #88. The
preparation implementation PR explicitly links those outcomes. Parent discovery
issues are not silently nominated as completed work. Keep every release-bearing
issue open. Retention is up to 90 days, subject to repository policy; an expired
artifact requires a new verified candidate, not borrowed acceptance.

## Exact-candidate test and acceptance matrix

Use disposable signets, local bare Git origins, native profiles and unrelated
project directories. Preserve native authentication in place; do not copy it,
rewrite a personal connection or use private memories as public fixtures.
Confirm source/manifest/runtime/Codex/Pi identities before tests. Capture full
fixture inventories and Git heads where a no-effects or delivery claim matters.

1. **Ordinary continuity and rendering (#13/#56/#65):** ask about a synthetic
   remembered project without naming Mandalore, correct it in the other harness,
   and recall current state/history from another directory. Verify stable record,
   supersession, device/harness attribution and another bank's isolation. Measure
   selected representation bytes separately from wire/native aggregate tokens;
   retain errors, conflicts and truncation faithfully. Ordinary learning should
   select one combined delivery operation when permitted, with no redundant sync.
2. **Consolidation and restrictions (#61/#65):** deliver a pending commit on a
   direct cue without filler records, then test useful new learning, quoted cue,
   no-sync local saves, and read-only/no-save refusal. Exercise offline, busy,
   cancellation and response ambiguity; inspect before retry and separate local
   durability from delivered Git heads. No automatic setup or conflict resolution.
3. **Historical retrieval (#57):** compact search → selected excerpt → deliberate
   expansion, later-passage and multi-document answers, negation, current versus
   historical evidence, source pins, stale refusal and complete requested review.
   Measure context savings independently from #56; no proof-of-absence claims
   from empty/truncated results and no incidental learning in read-only tests.
4. **Native connection lifecycle (#13):** install/inspect/update/repair in owned
   synthetic profiles; preserve unrelated state and expose partial failure.
   Startup/reload/new/resume/fork, interrupted work, fresh local context and
   repeated events must retain isolation without accumulating injections or
   duplicate tools. Verify offline/concurrent delivery and truthful receipts.
5. **Quota/recovery (#74):** repeat request-count/identity regressions and native
   synthetic quota displays with known/unknown retry timing, ordinary refusal,
   partial state and explicit recovery. Preserve default-No, Back, TUI/plain,
   no-color and narrow output; do not exhaust live public quota to test this.
6. **Readiness (#85):** missing/configured/unknown/historical/stale/malformed/
   unsupported/partial states for both harnesses, details/prompt and separately

   fixtures. Cover arrows/Vim/Back, default-No, EOF/Escape/Ctrl+C, color/no-color,
   80/32-column output and terminal restoration; retain actual recordings.
7. **Distribution/update (#88):** verify every retained payload, version/source
   stamping and eight-file manifest. Test owned isolated 1.0.0→1.1.0 CLI and
   native connection update plus recovery without changing memory/auth/session

## Acceptance and release boundary

The authorized human acceptor must review the exact nominated artifact and every
included issue's original criteria, then provide an actual verdict and durable
evidence for **Product acceptance**. Ordinary author-separation policy applies
except for the separately authorized [exact-candidate owner-review extension](../decisions/0002-mvp-owner-acceptance.md#explicit-110-scope-extension--2026-09-16)
recorded in #96: source `b89458617b49d2eb0a8686dcd75c26aa7ea6f6ba`, its exact
manifest, and the nine enumerated issues including #93. It is not reuse of the
old MVP scope or approval of another 1.1.0 candidate. The owner must personally
review, supply actual verdicts and confirm that review; agent-run checks do not
supply a human verdict. No actor configuration or acceptance dispatch is implied.

Publication requires the existing release gates and explicit authority. Promote
the same accepted bytes; never rebuild after acceptance. Verify downloadable
assets, installation/update/recovery and issue ledger before announcing release.
Until then, installation instructions continue pointing to published v1.0.0.
The known-good owned 1.0.0 installation is a rollback reference, not permission
to downgrade an incompatible future schema or delete newer memory. A rejected
candidate returns affected work to implementation and needs new nomination.
